# 旅行内容调研手册

这份手册写给两类读者：准备为一次新旅行填内容的朋友，以及替你做调研的 AI agent（Codex、Claude Code 等）。它把一次真实旅行项目里反复验证过的做法整理成可复用的方法：去哪里查、查到什么程度算数、怎么写进 `content/*.json`、怎么自检、哪些坑已经踩过。

手册只讲“怎么调研、怎么写”。字段的完整定义见 [content-schema.md](content-schema.md)；工程和发布经验见 [lessons-learned.md](lessons-learned.md) 与 [ios-delivery.md](ios-delivery.md)。

## 0. 开工前

### 0.1 先把约束问清楚

调研之前先拿到这些信息。缺哪一项就在调研记录里写成“待用户确认”，不要自己假设。

| 约束 | 用途 | 写在哪里 |
| --- | --- | --- |
| 目的地、出发地、旅行日期 | 决定开放日历、季节、日落、节假日 | `trip.json` 的 `destination`、`startDate`、`endDate`、`departureDate`、`homeCity` |
| 同行人数、年龄段 | 票价口径（成人/儿童）、订位人数、酒店入住人数 | `trip.json` 的 `partySize`；`hotels.json` 的 `adults`、`rooms` |
| 往返航班时刻与航站楼 | 第一天最早开始时间、最后一天最晚结束时间 | `flights.json`（只写航班号与时刻） |
| 作息：几点起床、几点出门 | 每天第一站的时间 | 调研记录；影响 `itinerary.json` |
| 兴趣与禁忌 | 地点取舍、餐饮偏好、体力上限 | 调研记录 |
| 是否已订酒店 | 首末段交通估算、就近休息 | `hotels.json`；未订时在行程说明“首末段为市中心估算” |
| 当地时区、币种 | 日期换算、预算、汇率 | `trip.json` 的 `timezone`、`currency` |
| 地图范围 | 坐标越界检查 | `trip.json` 的 `map.bounds` |

`trip.json` 要最先填好，因为 `scripts/verify_content.py` 会用 `startDate..endDate` 检查行程天数、用 `map.bounds` 检查所有坐标。

### 0.2 建一份当天的调研记录

每次调研开一份记录，放在 `docs/research/`，文件名用 `YYYY-MM-DD-主题.md`，内容从 [research-record.md](../templates/research-record.md) 模板复制。记录要回答：看了哪些页面、什么时候看的、得出什么结论、有没有冲突、改了哪些字段、下一步做什么。写进 JSON 的东西，都应该能在某份记录里找到来源。

### 0.3 工作流总览

```text
确认约束 → 按内容类型调研 → 写入 content/*.json
        → python3 scripts/verify_content.py            （结构门禁）
        → python3 scripts/verify_content.py --require-complete   （真实旅行的完整门禁）
        → python3 scripts/build_ios_resources.py        （生成 App 内置资源）
        → python3 scripts/verify_content.py --built-catalog      （确认生成物是最新的）
        → 调研记录收尾（写入字段、冲突、下一步）
```

`--require-complete` 会拒绝示例文字、`example.com` 链接、“待核实 / TODO”等占位词，以及覆盖太薄的内容。模板自带的京都示例能通过这道门禁；替换成你自己的内容后，只要还残留示例文字或占位词就过不了。

## 1. 通用证据规则

后面每一类内容都遵守这一节。碰到本节没覆盖的情况，按“宁可写不确定，也不写错”的方向处理。

### 1.1 证据分级

| 等级 | 来源 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| A | 运营方官网、政府/公共机构页面，在真实浏览器里打开并看到内容 | 开放时间、票价、规则、关闭公告、入境要求 | 当天实时状态（除非页面本身是实时系统） |
| B | 权威第三方完整名单（如当年米其林官方完整名单）、官方预约系统 | 名单完整性、荣誉、查询时的订位情况 | 菜单价格（要回餐厅官网查）、未来有位 |
| C | 预订平台（携程、Booking 类）、地图 POI（OpenStreetMap、Apple Maps、Google Maps） | 指定日期和人数的报价、地址候选、平台分类 | 官方星级、营业状态的权威结论 |
| D | 攻略、社交媒体（小红书等）、博客 | 拍照点、常用别名、游客关注什么、现场体验 | 价格、开放时间、规则、预约条件 |
| X | 模型记忆、未打开的搜索摘要、“印象中” | 什么都不能证明 | 一切 |

规则很简单：**写进 JSON 的事实至少要有 A 或 B 级来源**；C 级只用于报价、坐标候选这类本来就只能从平台拿到的数据，并照实标注平台口径；D 级只能用于补充“看什么、怎么拍、大家叫它什么”。

### 1.2 什么才算“查证过”

- **必须在真实浏览器里看到内容。** HTTP 200 不等于查到：很多官网是单页应用，命令行抓到的是空壳；有的旧链接 200 之后跳转到 404 页面或首页。这两种都不算查证。
- **动态内容要点开。** 营业日历要逐日点选、折叠的 FAQ 要展开、票价要选到具体日期和票种。只读页面静态部分得到的往往是默认值或旧值。
- **看页面自己的日期。** 找“更新于 / Last updated / 展期 / 有效期”。网站页脚的版权年份不是内容年份，不能据此推断“这是今年的名单”。
- **搜索摘要不算来源。** 摘要可能来自旧版本页面，还可能张冠李戴。例：搜索摘要写的地址和官网写的街道名不一致，最后以官网为准。
- **一个页面只证明它写了的东西。** 公园 24 小时开放，不代表园内独立收费的花园也 24 小时开放；街区“无统一营业时间”，不代表街上的寺庙、店铺全天开放；大楼营业到 22 点，不代表楼里某一层对外开放到 22 点。
- **抓取被拦截（403、验证码、安全验证）时**，换成真实浏览器打开；仍然打不开就记为“未能读取”，不能当成查到了现价。**不要尝试绕过验证码或机器人检测。**

### 1.3 二手来源的用途边界

攻略和社媒很有用，但只用在这些地方：

| 可以用来 | 不能用来 |
| --- | --- |
| 发现候选地点、拍照机位、游客常用的叫法 | 证明票价、开放时间、预约规则 |
| 给地点补一个大家搜得到的别名（写进 `name` 或 `desc`） | 证明某项目仍在展、某设施仍开放 |
| 了解常见坑（排队、暴晒、着装） | 证明“可以自带食物”这类规则 |
| 餐饮的现场实拍价格参考（明确标为历史实拍） | 当成当日菜单价 |

旧帖里的规则性说法（“可以自带零食”“半天就能玩完”“某项目当天去排队就能进”）如果与官方冲突，必须标成“个人经历 / 可能过时”，以官方为准。

### 1.4 三种数字要分开

价格至少有三种口径，写的时候必须说清楚是哪一种：

| 口径 | 含义 | 写法示例（`places[].price`） |
| --- | --- | --- |
| 官方价 | 官网当天显示的具体票种价格 | `官方票价 1,300 日元／人（成人一般票）` |
| 规划预算 | 为了算总账留出的金额，可以比官方价高 | `官方票价 1,300 日元／人；规划预算按 1,500 日元留余量` |
| 估算 | 没有官方价时的编辑估计 | `一日券按 1,100 日元／人做预算，非当日实价` |

- `places[].budget` 是每人规划预算（当地币），用于预算汇总，不是票价声明。
- 不要把居民价、会员价、多景点套票、夜场票、快速通道混进普通门票。
- 未选择日期看到的“起价”只是起价；要写具体价，就选到旅行当天、对应人数和票种。
- 小幅价格浮动不需要标成警告；影响能不能去的信息（需预约、展区关闭、只限住客）才需要醒目。

### 1.5 建议时段和开放时间是两件事

- `opening` 写运营方的开放信息：开放时间、最后入场、休息日、特殊日期。
- `bestTime` 写编辑建议：什么时候去最合适、为什么（光线、人流、避暑）。
- 两者分别展示，不要把“建议 16:00–18:30 去”写成“开放 16:00–18:30”。
- 行程里的停留时长、步行和等车时间都是规划估计，不是运营方承诺，也不是实时导航结果。

### 1.6 每条事实都要能追溯

- 每个地点、每份菜单、每条订位观察、每条酒店报价，都带 `checkedAt`（核对日期，`YYYY-MM-DD`）和来源 URL。
- 来源 URL 用具体页面（票价页、营业时间页、菜单 PDF），不要只写官网首页。
- 同一事实有多个页面时，写最直接的那一个；有冲突时两个都记进调研记录（见 1.13）。
- 来源必须是 `https` 链接，`verify_content.py` 会检查。

### 1.7 快照措辞

凡是会变的信息，措辞都要体现“这是某天查询看到的”：

| 不要写 | 要写 |
| --- | --- |
| 有位 / 还有空位 | 查询时显示 18:30、19:00 有双人位；这是快照，不代表实时余位 |
| 售罄 | 查询时所选日期未显示可订时段 |
| 开放 | 官网（核对日期）显示 10:00–18:00，最后入场 17:00 |
| 免费 | 官网写明普通时段免费；特殊活动另售票 |
| 最便宜 | 在（日期、人数、房数）条件下，平台显示的整段总价最低 |

只要是历史观察，就不要用“实时”“保证”“一定”这类词。`verify_content.py` 会拦截订位观察里的“实时有位 / 保证有位”之类表述。

### 1.8 不确定性要让用户看得见

- 不确定、有条件、需要预约、部分关闭的信息，要在界面上可见：**颜色 + 图标 + 文字**三者同时出现，不能只靠颜色（色弱用户、深色模式、截图转发时颜色都可能失效）。
- 约定俗成的分级：
  - 红色：明确关闭、不可用、会导致白跑一趟。
  - 橙色：需要预约、价格或条件未确认、只有部分开放。
  - 普通：一般的规划估计、小幅价格浮动。
- 写字段时直接把限定条件写进文本（例如 `opening` 写“雷雨或特别活动以现场公告为准”），而不是指望界面自动推断。

### 1.9 不做不可逆操作

调研过程中**只读不写**：

- 查酒店报价可以走到“填写入住人信息”那一步，看总价、税费和取消政策，然后停下。不填写个人信息，不提交订单，不付款，不领优惠券。
- 查餐厅订位只选日期、餐段、人数，看返回的时段，然后停下。不点确认，不填信息，不占位。
- 不提交任何表单，不发邮件、私信或咨询；需要联系酒店、景点、餐厅时，**起草文本**交给用户自己发。
- 不接受平台协议或 Cookie 以外的授权；Cookie 横幅选最少必要项。
- 不在任何地方输入证件号、银行卡号、密码。需要登录的平台由用户自己登录。

### 1.10 不编造

- 没有核实过的坐标就不给坐标，不要用区域中心点、城市中心点凑一个图钉。
- 没有合适授权的照片就不放照片，不拿别处、同名地点或旧照片冒充。
- 查询失败不等于售罄、不等于关闭、不等于不存在。
- 没找到合适的帖子，不要为了凑数放一篇错误或广告帖。
- 不编门牌号、邮编、电话、营业时间。

### 1.11 稳定 ID

- `places[].id`、`restaurants[].id`、`hotels[].id`、`preparation.items[].id`、`itinerary` 里每个 `uid`，一旦发布就不要改。照片、收藏、行程引用、勾选状态都挂在 ID 上。
- ID 用小写字母、数字、连字符（`verify_content.py` 会检查格式）。
- 地点改名、换了更准确的中文名，改 `name`，不改 `id`。
- 某项不再推荐时，优先从行程里移除或在文案里说明，不要删掉 ID 后再用同一个 ID 表示别的东西。

### 1.12 内容更新不碰用户状态

- `content/*.json` 是**打包进 App 的默认内容**。用户在 App 里改过的行程、勾选过的准备事项、保存的票据，存在本机工作区和（可选的）共享服务里。
- 新版本内容只影响还没有本机工作区的安装；已经编辑过的用户，默认行程不会被覆盖。这是有意的设计：不能因为你修正了一个推荐顺序，就把用户自己排好的行程冲掉。
- 因此内容调整如果需要用户知道（例如某景点临时关闭），要写在地点的 `opening`、`notice` 等文本里，让用户打开详情就能看到，而不是去改他们的行程。
- 不要把真实的私人数据（订单号、共享行程内容）写进 `content/`。

### 1.13 冲突要记录，不要猜

两个来源说法不同时：

1. 两个都记进调研记录，写明各自 URL 和读取时间。
2. 能判断的按优先级取：运营方自己的页面 > 第三方页面；具体页面 > 概览页面；有日期的 > 没日期的。
3. 判断不了的，JSON 里写保守版本并提示核对。

已经遇到过的典型冲突：

- 餐厅官网写“周一至周六晚餐”，美食指南页写“周一休息”：只把两边都认可的日子写成确定休息，周一保留“出发前再确认”的提示。
- 官网首页写“秋季菜单”，菜单链接点进去还是夏季菜单：不把夏季价格当成出行季的已核实价格。
- 官方“最后入场时间”和预约系统里出现的更晚时段不一致：以最终确认函为准，并在提示里写出来。
- 景点页面上方写“可预约”，同页下方残留“预约已关闭”：记为矛盾，建议用户先咨询官方。
- 菜单 PDF 没有写明是午餐还是晚餐：`meal` 用 `any`，提示预约时核对。

### 1.14 宁缺毋滥

- 发布时可以有缺口，但缺口要诚实：“本轮未核到价格”写成 `pricingStatus: unverified`，而不是填一个猜的数。
- “没找到合适照片”和“找到了但授权不合适”是两种情况，调研记录里分开写。
- 覆盖目标（例如每个地点 3 篇参考帖）是目标，不是指标；达不到就写明缺口和原因。

### 1.15 隐私

- 不写证件号、订单号、票号、取票码、会员号、电话、邮箱。`flights.json` 只写航班号和时刻。
- 不写同行人的真实姓名。
- 截图存证时裁掉个人信息；调研记录里不贴私人订单截图。
- 酒店邮件、入境卡字段表这类模板，把个人信息写成 `[占位]`。

## 2. 行程编排

### 目标字段

`itinerary.json`：

- `days[]`：必须和 `trip.json` 的 `startDate..endDate` 逐日一一对应。
- `days[].date`、`title`（当天主题）、`area`（片区走向，如“北岸 → 老城”）、`note`（当天总说明，写取舍理由）。
- `days[].items[]`：`uid`（全行程唯一、发布后不改）、`place`（引用 `places` 或 `dining` 的 ID）、`time`（`HH:mm` 或空字符串表示时间待定）、`durationMinutes`、`note`。
- `budget`：`flightOut`、`flightReturn`、`hotel`、`food`、`transport`、`other`。

### 来源优先级

1. 用户给出的硬约束（航班、起床时间、已订项目）。
2. 各地点官方开放时间、最后入场、休息日、特殊日期（逐日日历）。
3. 当地日落时间、气候均值（官方气象机构）。
4. 交通估算（地图服务的规划值，只作估计）。

### 步骤

1. **列约束，分硬软。**
   - 硬约束：航班起降、需预约的时段、演出场次（如固定时间的表演）、闭馆日、最后入场、返程到机场的最晚时间。
   - 软约束：建议时段、拍照光线、用餐时间、体力。
   - 硬约束决定骨架，软约束只在骨架里调整。
2. **按片区聚类。** 先把候选地点按区域分组（写进 `places[].zone`），一天只走一到两个相邻片区，避免跨城来回。
3. **定每天的起止。**
   - 第一天：从航班落地时间 + 入境 + 到酒店倒推；深夜或凌晨落地的，第一天上午留空。
   - 其余天：从用户的出门时间开始（例如 11 点出门，就不要把 9 点开门的项目放第一站然后假设他们会早起）。
   - 最后一天：从航班起飞时间倒推到机场的时间（值机、安检、交通、缓冲），最后一项的结束时间要早于这个点，并留余量。
4. **排顺序，留缓冲。**
   - 相邻两站之间留 15–45 分钟交通空档（按距离和交通方式）。
   - 中午和下午最热、最累的时候安排室内项目或休息。
   - 每天规划活动时长控制在约 7 小时以内；超过就删项，不压缩交通。
5. **日光规则。** 用户想要白天合照的地标，必须排在日落前；夜景单独安排。不要用一张夜景替代用户明确想要的白天照片。第一天如果因天气错过，给出“次日白天补拍”的调整方案。
6. **雨天替换。** 每个户外项目在 `places[].rain` 写一个**同片区**的室内替换，不要让用户下雨时跨城。
7. **整体替换而不是叠加。** 需要一整天的项目（主题乐园、远郊一日游），选它就整体替换那一天，不要和原片区叠加。在 `desc` 或 `tip` 写清“选它就取消某某”。
8. **写 `note`。** 每天的 `note` 写取舍逻辑和“累了先删哪一项”。

### 核对与校验

`verify_content.py` 会自动检查：

- 天数与 `trip.json` 一致、`uid` 唯一且格式正确、`place` 引用存在。
- `time` 格式为 `HH:mm` 或空；有 `durationMinutes` 就必须有开始时间。
- 当天时间递增、相邻项不重叠（按 `durationMinutes`，没有则按地点 `hours`）、单日计划时长上限（警告）。

人工再核对：

- [ ] 每一站的到达时间都在该地点开放时间内，并早于最后入场。
- [ ] 闭馆日没有排进行程（逐日核对，尤其是周一、节假日、特殊活动日）。
- [ ] 最后一天最后一项的结束时间满足返程余量。
- [ ] 单日活动时长约 7 小时以内（按实际体力调整）。
- [ ] 固定场次的项目（表演、导览）提前 15–20 分钟到场，并留离场时间。
- [ ] 户外项目都有同片区雨天替换。
- [ ] 需要预约的项目在 `tip` 或 `opening` 写明，并在行前准备里有对应事项。

### 常见坑

- 把“建议时段”排成“开放时间”，结果用户以为只能这时去。
- 街区散步项目默认全天开放，结果里面的宗教场所只在特定时段可入内，着装还有要求。写成“安排外观；入内另看访客时段与着装”。
- 海滩默认可以游泳：救生员值守时段之外、官方发布安全提示时，只安排岸上活动。
- 同一个园区里有多个分馆，开放时间和末入时间不同。
- 一个园区工作日和周末时间不同，或某几天提前闭园——改日期就要重看日历。
- 交通估算写成“需要 20 分钟”，而不是“约 20 分钟（规划估计）”。

### 完成标准

- [ ] `verify_content.py` 无错误；时间顺序、重叠、时长警告已逐条处理或在调研记录里说明原因。
- [ ] 每天有 `title`、`area`、`note`；`note` 写明取舍和可删项。
- [ ] 硬约束全部满足，并在调研记录列出核对依据。
- [ ] 首末两天与航班时刻核对过。

## 3. 地点与坐标

### 目标字段

`places.json` 的 `places[]`：

| 字段 | 写什么 |
| --- | --- |
| `id` | 稳定 ID，发布后不改 |
| `name` / `en` | 中文名（优先用游客搜得到的叫法）/ 英文或当地官方名 |
| `zone` | 片区，用于聚类和筛选 |
| `kind` | 类型（地标、博物馆、街区、观景、自然、主题乐园……） |
| `hours` | 建议停留小时数（规划估计） |
| `budget` | 每人规划预算，当地币；免费写 0 |
| `desc` | 一句推荐理由：为什么值得去、适合谁 |
| `tip` | 可执行的建议和限制：怎么走、怎么拍、需不需要预约、有什么限制 |
| `travel` | 怎么到（规划估计） |
| `rain` | 同片区雨天替换 |
| `food` | 附近吃什么 |
| `link` | 官方页面 |
| `opening` | 官方开放信息（含最后入场、休息日、关闭公告） |
| `price` | 价格口径（见 1.4） |
| `bestTime` | 建议时段和理由 |
| `guides` | 可选，结构化攻略（见第 9 节） |
| `sources` | `[{label, url}]`，至少一条 |
| `checkedAt` | 核对日期 |

`locations.json`：

- 文件级：`attribution`（数据来源与署名，例如 `© OpenStreetMap contributors`）、`license`（例如 `ODbL-1.0`）、`checkedAt`、`notes`（写明“坐标是参考点，不保证是入口”）。
- `locations.<地点ID>`：`name`、`address`、`coordinates`（`[纬度, 经度]`）、`source`。

### 来源优先级

- 地点内容：运营方官网 > 目的地旅游局 / 政府机构页面 > 其他。
- 候选发现：旅游局的“必做清单”类页面（用作覆盖面筛选，不当成人气排名）、攻略与社媒（发现拍照点和别名）。
- 坐标：OpenStreetMap 候选 + 当地官方测绘 / 地图机构抽查 > 运营方页面地址 > 地图应用。

### 步骤：地点内容

1. **广撒网列候选。** 旅游局主题页、官方分类清单、热门攻略、社媒，列出候选并标注来源类型。候选多不等于都要放进行程；二选一的项目（例如两个同类观景点）在 `desc` 里写清楚。
2. **逐个打开官网核实。** 开放时间、最后入场、休息日、票价（选到具体日期和票种）、预约要求、当前关闭或维修公告、展期。
3. **找限制条件。** 只限住客、只限预约、只限某餐厅顾客、只对某年龄开放、着装要求、禁带物品、某展区关闭、施工绕行、天气暂停。
4. **写文案。** `desc` 一句话讲清为什么去；`tip` 写具体动作和限制；不要把普通商场、咖啡馆包装成“必打卡”。
5. **填 `sources` 和 `checkedAt`。**

### 步骤：坐标

1. **按名称、类型、地址在 OpenStreetMap 里找候选。** 用 Nominatim 网页或 Overpass 查询，同时比对名称（中英文/当地语言）、要素类型（`tourism=attraction`、`amenity=restaurant` 等）和地址。
2. **拒绝错误匹配。** 常见的错误候选：同名的地铁站、公交站、停车场、快递柜、同名酒店、旅行社、景区里的某个小设施。凡是类型对不上的都拒绝。
3. **抽查一部分。** 用当地官方测绘/地图机构的公开地图或搜索服务核对几处关键地点（尤其是新开业、搬迁过或 OSM 标注不完整的地点）。
4. **国界过滤。** 边境城市或和邻国有同名地点时，检查候选的国家/地区代码与 `trip.json` 的 `destination.countryCode` 一致，拒绝跨境同名结果。
5. **范围检查。** 所有坐标必须落在 `trip.json` 的 `map.bounds` 内（`verify_content.py` 会检查）。越界的通常是选错了同名地点。
6. **写署名和许可证。** 使用 OSM 数据就在 `locations.json` 文件级写 `© OpenStreetMap contributors` 和 `ODbL-1.0`，并在 App 的“关于”里保留署名。
7. **不猜。** 没有确定地址的项目（例如不对外开放的场所、休息模块）不提供坐标，宁可让地图不显示这一站。

### 核对与校验

- [ ] `verify_content.py`：来源 `https`、`checkedAt` 合法、坐标在 bounds 内、`locations` 的 ID 都能对应到地点。
- [ ] `--require-complete`：每个地点都有坐标（没有坐标的必须在调研记录说明原因，并判断是否接受这个门禁失败）。
- [ ] 抽查 3–5 个坐标：在地图应用里打开，确认落在正确的建筑或区域。
- [ ] 所有 `opening` 里的时间和 `sources` 链接指向的页面一致。

### 常见坑

- 大型建筑、园区的参考坐标是几何中心，可能不在任何入口附近，步行路线可能算不出来。`notes` 写明“参考点不保证是入口”。
- 同一地点有新旧两个地址（搬迁、新园区），旧攻略还在用旧地址。
- 地图应用把某个地点标为“永久关闭”：这只是当时地图的标签，要去官方渠道确认，不能直接当事实写进文案。
- 地址里写“新城区 / 某某大道”的搜索摘要和官网的街道名不一致——以官网为准。
- 中文名五花八门：选游客最常用的叫法，其他叫法写进 `desc`，方便搜索。

### 完成标准

- [ ] 每个地点都有 A 级来源和 `checkedAt`。
- [ ] 每个地点都有 `rain` 和 `bestTime`；需要预约或有限制的写在 `tip` / `opening`。
- [ ] 坐标全部来自可追溯来源，文件级署名和许可证齐全；没有凭空生成的图钉。
- [ ] 调研记录里列出被拒绝的候选及原因（至少对容易混淆的地点）。

## 4. 照片

### 目标字段

`photo-sources.json` 的 `albums.<地点ID>.photos[]`：

| 字段 | 写什么 |
| --- | --- |
| `file` | 仓库内路径，如 `media/photos/<地点ID>-1.jpg`（相对 `content/`） |
| `caption` | 说明拍的是什么；只拍到外观就写“外观” |
| `sourceUrl` | 原始文件页面（不是缩略图地址） |
| `creator` | 作者（按来源页署名要求原样写） |
| `license` | 许可证名称，如 `CC BY-SA 4.0` |
| `licenseUrl` | 许可证链接 |
| `date` | 拍摄日期（来源页标注的） |
| `downloadUrl` | 可选，原图下载地址；照片处理脚本据此下载原图到本地缓存 |

### 来源优先级

1. Wikimedia Commons 等开放许可图库（CC0、CC BY、CC BY-SA；注意 SA 的相同方式共享义务）。
2. 运营方明确允许媒体使用的素材（要看到书面授权条款）。
3. **不使用**：写明 All Rights Reserved 的官网照片、社媒图片、搜索引擎图片、酒店平台图库——除非拿到授权。已经找到但授权不合适的官方素材，列给用户决定，不默认使用。

### 步骤

1. 在 Commons 上按地点名、英文名、当地语言名搜索，也看对应的分类页（Category）。
2. **逐张目视检查。** 每张都要打开大图看，不能按缩略图批量选。
3. **每个地点 3 张，角度不同**：远景/全景、近景/细节、有代表性的场景。三张都差不多的角度时宁可少放。
4. **排除这些图：**
   - 合成图、后期加了特效/文字/边框的宣传图、拼贴图。
   - 过时的场景：旧版演出、已拆除或改造的设施、搬迁前的旧址。
   - 普通游客进不去的区域：只限住客的设施、员工区域、需要特殊许可的内部。
   - 已关闭展区作为主图（会暗示“去了能看到”）。
   - 同名的其他地点（另一个国家的同名景点、另一座城市的同名街道）。
   - 画质差、主体不清、水印明显的图。
5. **视频截帧要写明。** 从 Commons 视频截取的帧，`caption` 注明“视频截帧”，不冒充摄影原片。
6. **只有外观的写清楚。** 私人建筑、机构只能拍外观时，`caption` 写“某建筑外部；非内部”，不暗示可以进入。
7. **下载原图到本地缓存。** 在条目里写 `downloadUrl`，运行 `python3 scripts/build_photos.py --download-missing`：原图下载到不进 git 的缓存目录（默认 `.photo-cache`），只有处理后的文件写到条目的 `file` 路径（`content/media/photos/`）。脚本的具体参数以 `--help` 为准。
8. **处理图片。** 脚本的处理口径：
   - 按 EXIF 方向转正。
   - 去掉元数据（EXIF、GPS），只保留像素。
   - 长边不超过 1200 px，JPEG 单张不超过约 180 KB（先降质量，质量降到下限再缩尺寸）。
   - 对处理后的文件算 SHA-256，全库去重，重复的直接报错。
   - 下载时请求之间有间隔，并带明确的 User-Agent，对图库保持礼貌。
9. **写来源字段**，每张都填全。

### 核对与校验

- [ ] `verify_content.py`：文件存在、`creator`、`license`、`licenseUrl`、`sourceUrl` 齐全。
- [ ] 在 App 里逐个打开相册，确认每张都能加载、署名显示正确。
- [ ] 调研记录列出每个地点被排除的候选和原因。

### 常见坑

- 以为 Commons 上的都能随便用：CC BY-SA 要求署名和相同方式共享，个别文件还有人格权、商标、建筑全景自由度的额外说明，逐张看。
- 选了一张漂亮的夜景，结果是多年前的旧样子，现场早已改建。
- 选了“需另购票”区域的照片，用户以为买普通票就能进。
- 照片其实拍的是另一个国家的同名地点。
- 原图进了 git，仓库体积暴涨；原图应只留在本地缓存。

> 照片只证明“拍摄时是这个样子”，不证明现在可以进入、仍然开放或场景未变。

### 完成标准

- [ ] 每张照片都有完整的来源、作者、许可证、拍摄日期，并经过人工目视。
- [ ] 每个有相册的地点 1–3 张（目标 3 张），角度不同，无重复。
- [ ] 所有处理后的文件符合尺寸、体积要求，无元数据，SHA-256 不重复。
- [ ] 没有授权不明的图片。

## 5. 社媒参考帖

社媒（小红书等）上的真实游记能告诉你“别人实际怎么玩、在哪拍、踩了什么坑”。它们是 D 级来源，并且涉及版权，所以规矩比其他内容多。

### 目标字段

`posts.json` 的 `posts[]`：

| 字段 | 写什么 |
| --- | --- |
| `id` | 稳定 ID（可以用平台的帖子 ID 派生，但要满足 ID 格式） |
| `platform` | 平台，如 `xiaohongshu`、`web` |
| `title` | 原帖标题（原样） |
| `author` | 平台显示的作者名 |
| `date` | 平台显示的日期；“编辑于”不能写成首次发布日期 |
| `heat` | 互动数快照，写明是采集时的数字；只有平台明确显示数字时才写数字 |
| `url` | 原帖链接 |
| `capturedAt` | 采集日期 |
| `categories` | 分类，如 `整体`、`拍照`、`目的地`、`酒店`、`餐饮` |
| `summary` | **你自己写的**编辑摘要，不复制原文 |
| `images` | `[{file, order}]`，`order` 从 1 连续编号 |
| `guidePlaces` | 这篇帖子实际讲到的地点 ID |

### 版权与授权（最重要）

- **公开仓库不能包含未经授权的帖子图片和正文。** 模板是公开仓库，所以默认只保留：标题、链接、作者、日期、你自己写的摘要，以及你有权使用的图片（自己拍的、自绘的、明确授权的）。
- 私人使用的 fork 里保存原图，也要只在**得到明确许可**时才逐字节保存，并且不要把这样的 fork 公开。
- 不要把原帖正文复制进 `summary`。摘要要短、要用你自己的话，讲清这篇帖子对规划有什么用。

### 来源优先级（选帖）

1. 近期（出行前一年内）、实际去过、有具体路线和实拍的帖子。
2. 能补充官方没写的信息：机位、排队经验、步行路线、现场环境。
3. 高互动帖子不一定准确；**准确 > 热门**。

### 步骤

1. **用已登录的真实浏览器读完整原帖。** 由用户自己登录平台账号。搜索结果卡片、缩略图不能代替原帖。
2. **读正文和全部图片。** 按轮播顺序看，记下哪些图对应哪个地点。
3. **判断是否入选**，按下面的排除标准。
4. **写记录。** 标题、作者、日期（原样）、链接、互动快照、采集日期、分类、自己的摘要、关联地点。
5. **图片（仅在有授权时）：**
   - 按轮播顺序保存，`order` 从 1 开始连续。
   - 排除头像、评论区图片、广告图、轮播的重复复制项。
   - 保存平台提供的原始文件，不二次压缩、不裁剪、不去水印、不加字；记录每张的字节数和 SHA-256。
6. **App 跳转。** 小红书原帖可以用 `xhsdiscover://item/<noteId>` 唤起 App（`noteId` 是原帖 URL 路径最后一段），唤起失败再回退到网页链接。模板里 `ExternalLinks.swift` 负责这个策略。能发出跳转请求不等于在目标 App 里打开成功，真机上要单独验证。

### 覆盖目标（可按旅行调整）

- 整体攻略：约 5 篇，覆盖不同节奏（懒人版、慢游、紧凑版）。
- 每个主要地点：约 3 篇攻略；拍照类 1–3 篇。
- 酒店：候选酒店各 1 篇实住帖（只关联同一家店，同品牌不同分店不能混用）。
- 达不到的在调研记录里列出缺口和原因（“检索结果多为广告/地点混淆/内容错误”）。

### 排除标准（附示例）

| 排除原因 | 示例 |
| --- | --- |
| 地理错误 | 手绘地图把景点方位和距离画错 |
| 事实错误 | 把收费观景台写成免费；写了错误的地铁站 |
| 过时 | 已被新帖替代的旧节日主题；已涨价的旧票价；搬迁前的旧址 |
| 混淆地点 | 把两个相邻的摊位、两家同名店混为一谈 |
| 与官方冲突且无价值 | 建议绕开园区限制、规避规定 |
| 广告/软文 | 通篇推广某商品，没有实游内容 |
| 视频帖冒充图文 | 视频内容不能当图文帖收录 |
| 只为凑数 | 泛泛的“十大必去”榜单 |

### 核对与校验

- [ ] `verify_content.py`：ID 唯一、URL 为 `https`、`capturedAt` 合法、`images.order` 为 1..n、文件存在、`guidePlaces` 引用有效。
- [ ] 同一原帖只收录一次（跨多个地点的游记只存一份，用 `guidePlaces` 关联多个地点，不要用关联数冒充帖子数）。
- [ ] 有图片时，逐张核对：字节数、SHA-256、顺序、来源 URL 不重复。

### 常见坑

- **Live 图重复帧。** 小红书的 Live 图首图在页面里同时有播放器静态帧和浮层静态帧两个图片节点，两个 URL 只有协议不同（`http://` 与 `https://`）。批量采集会把同一张图存两次。对策：每个轮播项只取第一张图；校验时把 URL 去掉协议后去重。
- 把“编辑于 07-25”写成发布日期。
- 把原帖的票价、开放时间当成新事实写进地点资料。原帖里的价格、规则只属于原作者的体验。
- 把观众背影、工作人员、动物特写当成“人像参考”凑数。
- 把原作者的“家庭出游”“学生票”经验改写成通用规则。

### 完成标准

- [ ] 每篇入选帖都读过完整原帖，摘要是自己写的。
- [ ] 公开仓库里没有未授权的原帖图片和正文。
- [ ] 覆盖情况和缺口写进调研记录。
- [ ] 原帖里的价格、开放、预约信息没有进入正式地点资料。

## 6. 酒店

### 目标字段

`hotels.json`：

- 文件级查询条件：`checkIn`、`checkOut`、`adults`、`rooms`、`currency`（报价币种）。
- `hotels[]`：`id`、`name`、`en`、`region`、`reason`（推荐理由）、`notice`（醒目提示：无窗、装修、条件限制）、`rating`（平台评分，原样写平台口径）、`address`、`coords`、`coordinateSource`、`source`、`checkedAt`、`policies`（入住退房时间、押金、前台）、`transport`（到交通站的距离，写明是平台距离）、`photo`（`{file, source}`）、`rooms[]`、`tier`。
- `rooms[]`：`name`、`area`、`bed`、`view`、`quote`。
- `quote`：`status`（`available` / `pending` / `unavailable`）、`totalHome`（整段入住总价，出发地币种）、`breakfast`、`cancel`、`confirmation`、`extraFees`。

### 来源优先级

1. 预订平台在固定查询条件下的“填写入住人”页面（最终价格明细）。
2. 酒店官网（房型、政策、设施、装修公告）。
3. 平台酒店详情（地址、坐标、平台分类、政策）。

### 步骤

1. **固定查询条件。** 入住日期、晚数、成人数、房间数、币种，写进文件级字段。所有报价必须是同一组条件。深夜/凌晨抵达的，入住日期从前一天开始（并按晚计费）。
2. **列候选。** 按片区和预算档筛选，写 `region`、`tier`。
3. **逐个查房型。** 在平台里选到具体房型和价格方案，进入“填写入住人信息”页，读：
   - 整段总价明细（含税费），而不是列表页的每晚价。
   - 早餐、取消政策（免费取消截止时间、之后的罚金）、确认方式。
   - 入住人数限制（有的低价方案只限 1 人入住）。
   - 适用人群限制（有的方案不适用于某些国籍或年龄）。
   - 到这一步**停下**：不填个人信息，不提交，不付款，不领券。
4. **写报价。**
   - `totalHome` 取整段明细里的总价，**不要用每晚价 × 晚数**（四舍五入、逐晚价格不同、税费计算方式都会造成偏差）。
   - 含优惠的价格要看优惠条件：新客优惠、会员价、限时补贴、需要领券的——条件无法确认的，`status` 写 `pending`，在 `extraFees` 或 `notice` 里说明条件，这类报价**不参与价格排序**。
   - 到店支付外币、线上另收担保金的方案，写明币种与担保规则；折算价只是参考，不和固定总价混排。
5. **核对房型事实。**
   - 平台的“钻”“星”是平台分类，不等于官方认证星级；`rating` 按平台原文写。
   - “大床或双床”不保证大床。如果用户要求保证大床，这类房型不进推荐。
   - 无窗、景观不确定（酒店名里有“景观”不代表房间看得到景观）、正在装修的要写进 `notice`，醒目展示。
   - 城景和海景、不同方向的景观是不同房型，不要混写。
6. **深夜到店。** 如果航班深夜到达，起草一封请酒店保留房间、不要标记未到店的邮件，放进行前准备的 `copy` 字段，由用户自己发送。平台页面写“整晚保留”不等于和酒店达成了书面约定。
7. **坐标与照片。** 坐标用平台或官网公布的位置，写 `coordinateSource`；照片必须有使用权（见第 4 节），没有就用模板占位图或留空，不要用平台图库。

### 核对与校验

- [ ] `verify_content.py`：`available` 报价必须有正数 `totalHome`；坐标在 bounds 内；`source` 为 `https`、有 `checkedAt`；照片文件存在。
- [ ] 所有报价的查询条件一致（日期、晚数、人数、房数、币种）。
- [ ] 每个 `pending` 都写明了原因。
- [ ] 没有任何酒店因为查询失败或条件价被写成“售罄”。

### 常见坑

- 列表价和最终页价格不一样：以最终页明细为准，并在调研记录里记一笔。
- 忘记担保金：到店付款的方案可能另外冻结一笔担保金，退房后数个工作日才释放。
- 把平台“到地铁站 300 米”写成“步行 3 分钟”。平台距离不等于步行耗时。
- 只看了基础房型的“大床或双床”，就推荐给要求大床的用户。
- 忽略装修公告：有的酒店在预订页底部有分阶段装修提示，影响体验。

### 完成标准

- [ ] 每个报价都来自同一查询条件下的最终价格页，并有 `checkedAt`。
- [ ] 条件价全部为 `pending` 且不参与排序。
- [ ] 无窗、装修、床型不保证、景观不确定等信息都在 `notice` 里。
- [ ] 没有提交任何订单或联系酒店；深夜到店邮件是草稿。

## 7. 餐饮

餐饮内容最容易出错：价格有税费和服务费、菜单分午晚、订位情况随时变化。这一节最细。

### 目标字段

`dining.json`：

- 文件级：`version`、`checkedAt`、`currency`。
- `directory`：完整性锚点——`edition`（名单年份）、`status`、`sourceURL`（官方完整名单页）、`notes`、`counts`（按星级的数量，如 `{"1": 30, "2": 8, "3": 3}`，必须与名单一致）。
- `restaurants[]`：
  - 身份：`id`、`name`、`en`、`zone`、`type`、`cuisines`、`address`、`coordinates`（`{latitude, longitude}`）。
  - 荣誉：`award` = `{kind, stars, year, sourceURL}`。
  - 菜单：`menus[]` = `{name, meal, price, priceMax, basis, tax, includes, sourceURL, checkedAt, serviceChargePercent, taxPercent}`。
  - 预约：`booking` = `{url, policy, releaseRule, cancellation, availability, checkedAt, observations[]}`。
  - 订位观察：`observations[]` = `{date, meal, partySize, status, detail, checkedAt, sourceURL}`。
  - 其他：`hours`、`durationMinutes`、`closedWeekdays`、`closedDates`、`tips`、`sources[]`（`{title, url, checkedAt}`）、`depth`、`checkedAt`、`pricingStatus`。
- `recommendations[]`：`{id, title, day, meal, restaurantIDs, reason}`（`day` 是从 0 开始的行程日序号）。
- `guides[]`：`{id, title, summary, body, restaurantIDs, sources}`。

### 枚举值

| 字段 | 可选值 | 说明 |
| --- | --- | --- |
| `type` | `restaurant`、`foodCourt`、`stall`、`casual` | 正式餐厅 / 多摊位美食广场 / 单摊 / 休闲餐饮 |
| `depth` | `detailed`、`light`、`directory` | 深入核验 / 轻量小吃 / 仅名单收录 |
| `award.kind` | `stars`、`bibGourmand`、`selected`、`none`、`unverified` | 星级 / 必比登 / 指南入选 / 无 / 未核实 |
| `menus[].meal` | `breakfast`、`lunch`、`dinner`、`snack`、`allDay`、`both`、`any` | `any` 用于来源未限定餐段 |
| `menus[].basis` | `perPerson`、`estimate`、`perDish`、`perSet`、`perTable`、`marketPrice` | 价格的计量方式 |
| `menus[].tax` | `nett`、`++`、`unknown` | 已含 / 另加 / 未注明 |
| `booking.availability` | `notChecked`、`unknown`、`notRequired`、`walkIn`、`available`、`full`、`soldOut` | 总体预约情况 |
| `observations[].status` | `available`、`full`、`soldOut`、`waitlist`、`closed`、`notReleased`、`notChecked`、`unknown`、`blocked` | 单次查询结果 |
| `pricingStatus` | `verified`、`estimate`、`unverified`、`unknown`、`notPublished` | 价格核验状态 |

`recommendations[].meal` 和 `observations[].meal` 只能用 `breakfast`、`lunch`、`dinner`、`snack`。

### 来源优先级

1. **完整性锚点**：当年官方完整名单（如米其林指南当年发布的完整名单文章，写明发布日期和各星级数量）。
2. 餐厅官网：菜单页、菜单 PDF、预约页、公告（临时休息、菜单更换）。
3. 餐厅官网链接到的预约系统（TableCheck、OpenTable 类）。
4. 美食指南的动态餐厅目录（核对名称、星级、地址、菜系）。
5. 当地税务机关页面（现行消费税/增值税税率）。
6. 小吃、美食广场与市场：旅游局、经营方页面；社媒实拍价只作历史参考。

### 步骤

1. **确定完整性锚点。** 找到官方完整名单，记下发布日期、作者、各星级数量，写进 `directory`。之后用动态目录逐级筛选、翻页，确保名单里每一家都在 `restaurants` 里（`depth: directory` 也算收录）。数量对不上就停下查原因。
2. **逐家打开餐厅页。** 名单里的每一家都打开美食指南页和官网，核对：名称、星级（今年的，不沿用去年的）、菜系、现址（搬迁很常见）、官网入口。
3. **深入核验的餐厅（`depth: detailed`）：**
   - 找官方菜单：午餐、晚餐、素食、品鉴套餐分开，每一项单独一条 `menus`，各自带 `sourceURL` 和 `checkedAt`。
   - PDF 菜单：先提取文本，再**人工看一遍页面**（排版、价格与菜名对应、脚注里的服务费和税）。
   - 普通请求被拒（HTTP 403）时，在真实浏览器打开官网，截图读价格，截图存进调研证据（不进产品包）。
   - 通过官网链接的第三方菜单平台拿到的 PDF，要核对菜单年份和季节，不要沿用搜索摘要或去年价格。
4. **税费和服务费。**
   - `++` 只表示“另加费用”，不能默认服务费就是某个比例。只有官方写明具体费率时，才填 `serviceChargePercent`。
   - 税率从当地税务机关页面核对，写进 `taxPercent`，并在调研记录留链接。
   - 未注明含税与否的，`tax` 用 `unknown`，界面上不能写“必定另加”。
5. **特殊计价。**
   - 全桌同选的套餐、两人起订的套餐，在 `includes` 写明。
   - 多人宴席（例如 8–10 人桌）不能除以人数当成两人可点的人均。
   - 不公开价格的写 `pricingStatus: notPublished`；本轮没查到的写 `unverified`（不代表餐厅不公开）。
6. **荣誉。**
   - 美食广场、市场本身不挂星级；里面没有逐摊核定荣誉的，`award.kind` 用 `none`。
   - 必比登、指南入选不能写成星级。
   - 单摊的荣誉要看该摊自己的指南页面，不能外推到整个广场或市场。
7. **订位观察（快照）。**
   - 从**餐厅官网上的预约入口**进入预约系统，只选日期、餐段、人数（等于 `trip.json` 的 `partySize`），读返回的时段，然后停下。
   - 每次查询写一条 `observations`：日期、餐段、人数、状态、详情（具体时段、区域如室内/户外/吧台）、查询时间、来源 URL。
   - “候补（waitlist）”和“无线上可订时段”是两种状态；“无线上时段”也不等于全满（可能电话可订、未放号）。
   - 查询结果永远是快照：`detail` 写“查询时显示……”，不写“有位”“实时”。
   - 发现公告里的临时休息日期，写进 `closedDates`；固定休息日写进 `closedWeekdays`（ISO 编号：1=周一 … 7=周日）。
8. **小吃和美食广场的预算。**
   - 用 `basis: estimate` 和 `tax: unknown`，写一个区间（例如单人一餐 `price` 8 – `priceMax` 15）。
   - 在 `includes` 写清组成：主食参考 + 饮品/加点预留。后半段是预算预留，不是实测报价。
   - 社媒实拍价目表可以作为直接参考，但要写明是“某时期实拍标价”，不是出行当天价格。没有直接证据的单摊不写精确单价。
9. **推荐。** `recommendations` 按行程日和餐段给出候选，`reason` 写清地理和时间上的理由（“离下一站步行可达”）。**推荐不代表有位**，加入行程不代表订好。

### 核对与校验

`verify_content.py` 会检查：枚举值、`https` 来源、`checkedAt`、`observations` 的日期在行程内、人数等于 `partySize`、不宣称实时有位、`directory.counts` 与星级数量一致；`--require-complete` 下，`detailed` 餐厅必须有带来源的价格（或 `notPublished`）和预约链接，有星级餐厅就必须有 `directory.counts`。

人工再核对：

- [ ] 名单数量与官方完整名单一致，逐家打开过。
- [ ] 今年变化的条目（升降星、新入选、搬迁）已更新，没有沿用旧资料。
- [ ] 午餐卡片没有显示晚餐价。
- [ ] 所有 `++` 价格：只有官方写明费率时才算含税价。
- [ ] 每条订位观察都来自餐厅官网链接的预约系统，且没有点确认。

### 常见坑

- 用网站页脚年份判断名单年份。
- 把去年一星、今年二星的餐厅写成一星。
- 把“查询时没有线上时段”写成“订满”。
- 把整个美食广场或市场标成获奖单位。
- 把 `++` 当成固定比例的服务费。
- PDF 只提取文本不看版面，结果价格和菜名错位。
- 用搜索摘要里的菜单价格（往往是旧的）。
- 官网写“周一至周六营业”，指南写“周一休息”，直接选了其中一个（见 1.13）。

### 完成标准

- [ ] `directory` 写明官方完整名单来源、日期和数量，`counts` 与收录一致。
- [ ] `detailed` 餐厅的每一份菜单都有 `sourceURL` 和 `checkedAt`，午晚分开。
- [ ] 所有订位信息都是带时间戳的快照，措辞无“实时”“保证”。
- [ ] 未解决的价格和冲突在调研记录中逐条列出。
- [ ] 小吃预算明确是估算。

## 8. 行前准备

### 目标字段

`preparation.json` 的 `items[]`：

| 字段 | 写什么 |
| --- | --- |
| `id` | 稳定 ID；已发布的 ID 保留，用户的勾选挂在上面 |
| `group` | 按“什么时候做”分组：如“现在确认”“出发前 3 天”“出发当天打包”“出门前”“当地注意”“返程前一晚” |
| `title` | 一件具体的事；重要物品单独成项（转换插头、流量卡、现金、交通卡） |
| `summary` | 一句话概括 |
| `body` | 方法 + 完成标准，最后一段以“完成标准：”开头 |
| `copy` | 可选，可复制的模板文本（邮件、字段清单），个人信息写成 `[占位]` |
| `dueDate` | 可选，最早该处理的日期（`YYYY-MM-DD`，不晚于行程最后一天）；为空表示随时可做 |
| `links` | 官方来源 `[{label, url}]` |

`flights.json`：`flights[]` = `{id, number, from, to, departure, arrival}`，时间是各自机场的当地时间（`YYYY-MM-DDTHH:mm`）。只写航班号和时刻，不写订单号、票号、票价。

### 来源优先级

1. 目的地政府移民局官网（入境要求、免签条件、电子入境卡）。
2. 目的地卫生/药品监管机构（个人携带药品，尤其是受管制药品）。
3. 目的地海关（禁止和限制携带物品）。
4. 本国外交部门、目的地旅游局（安全提示、当地规定）。
5. 银行卡组织、发卡行、手机厂商（境外支付、ATM 取现、eSIM 支持）。
6. 交通运营方（交通卡、银行卡乘车）。

### 步骤

1. **在出发前（尽量接近出发日）读官方页面。** 规则会变。每条事项记下当天核对的页面和日期。
2. **区分“普遍要求”和“有条件要求”。**
   - 普遍要求：所有旅客都要做（例如在开放窗口内填写电子入境卡）。
   - 有条件要求：只有某些人要做（携带受管制药品需要提前若干周申请；来自特定地区需要疫苗证明）。有条件的写成“如果……则……”，不要写成人人必做。
   - 建议项（旅行保险、现金金额、流量大小）写成参考，不写成要求。
3. **按“何时做”分组，并设 `dueDate`。**
   - 窗口类事项（例如“抵达前若干天内才能填写”）：`dueDate` 设为窗口开始日，正文写清窗口（含不含抵达当天）。
   - 打包类：出发当天或前一天。
   - 返程复查：返程前一晚。
   - App 的“今日”页只显示 `dueDate` 已到（或为空）且未完成的事项，所以 `dueDate` 决定用户什么时候看到提醒。
4. **每项写方法和完成标准。** 例：“完成标准：收到确认邮件并离线保存。”完成标准要能判断“做完了没有”。
5. **写可复制模板。** 酒店深夜到店邮件、入境卡需要准备的字段清单（字段名，不填个人信息）、给酒店或景点的咨询邮件——写进 `copy`，由用户自己发送。
6. **支付与网络。** 分开写：商户是否受理某种支付方式、银行卡境外交易资格、酒店押金对卡的要求、ATM 取当地现金的扣款与换汇方式、动态货币转换（DCC）要选当地币种。不知道用户的银行和卡种时，写成“按发卡行规则核实”，不假定可用。
7. **不写个人信息。** 证件号、订单号、会员号都不写。`verify_content.py` 会拦截看起来像证件号的字符串。

### 核对与校验

- [ ] `verify_content.py`：ID 唯一、`group`/`title`/`body` 齐全、`dueDate` 合法且不晚于行程结束、链接 `https`、无疑似证件号。
- [ ] `--require-complete`：至少 10 项。
- [ ] 每个窗口类事项的日期窗口与官方页面一致（注意是否包含抵达当天）。
- [ ] 有条件要求没有被写成普遍要求。

### 常见坑

- 电子入境卡的开放窗口算错一天（是否含抵达当天）。
- 把“建议买保险”写成入境要求。
- 把受管制药品的提前申请期写成“出发前再说”——这类事项要放进“现在确认”组，并设最早的 `dueDate`。
- 旅游局、海关页面抓取不到完整条款，就当成“已全量核实”。抓不到就写抓不到，给出官方入口让用户自己看。
- 用户已经订好机票，还保留“去买机票”的事项；应改成“临行复查航班”，不动已有勾选。
- 删除旧事项后，把旧 ID 挪给新事项，导致新事项显示“已完成”。

### 完成标准

- [ ] 每项都有方法、完成标准和官方来源（如适用），并记录核对日期。
- [ ] 分组按“何时做”，窗口类事项的 `dueDate` 正确。
- [ ] 模板文本可直接复制，个人信息为占位符，没有替用户发送。
- [ ] 航班只有航班号和时刻。

## 9. 景点攻略

需要一整天或规则复杂的地点（主题乐园、需要预约的场馆），在 `places[].guides` 里写结构化攻略。

### 目标字段

`places[].guides[]`：`id`、`title`、`summary`、`updatedAt`、`sections[]`（`{title, paragraphs[]}`）、`links[]`（`{label, url}`）。

常见的三篇：选日与购票、一日路线、交通饮食与避坑。

### 来源优先级

1. 官方营业日历（逐日点选）。
2. 官方票种页、快速通道条款页。
3. 官方计划停运/维修公告页。
4. 官方 FAQ（外带食物、储物柜、安检、婴儿车等）。
5. 官方 App 的功能说明（实时排队、场次）。
6. 社媒游记：只补充路线经验，规则类说法标注“个人经历/可能过时”。

### 步骤

1. **逐日点开营业日历**，记下旅行期间每一天的开放时间。不同日期闭园时间可能不同。
2. **读票种条款。** 普通日票包含什么、不包含什么（夜场活动、快速通道通常另计）；快速通道的规则（每个项目几次、是否指定日期、是否包含门票）。
3. **读停运公告。** 旅行期间计划停运的项目、停演的表演；注明“计划之外可能另有停运”。
4. **读 FAQ。** 外带食物、储物柜、安检、雨天政策。需要展开的问答要逐个展开。
5. **写建议。** “推荐某天去”是规划判断（开放时间更长、和其他安排更顺），**不是低客流保证**，要明确写出来。
6. **标注旧说法。** 游记里的“半天刷完”“可以带零食”“储物柜多少钱”等，与官方冲突或无法核实的，标为个人经历或旧信息。
7. **写 `updatedAt` 和 `links`。** 每篇攻略写核对日期，链接指向具体官方页面。

### 核对与校验

- [ ] `verify_content.py`：每篇攻略有 `title`、`updatedAt`、`sections`。
- [ ] 日历、票价、停运信息都注明了核对日期。
- [ ] 规划预算（门票、餐饮、交通）明确标为预算而非报价。

### 常见坑

- 只看日历默认显示的那一天。
- 把快速通道写成“包含门票”。
- 把某个特别活动（需另购票的夜间活动）当成普通日票的一部分。
- 攻略正文维护了两份（例如网页一份、App 一份），后来只改了一份。模板里只维护 `content/places.json` 这一份。

### 完成标准

- [ ] 每一天的开放时间逐日核对过。
- [ ] 票种、快速通道、停运、FAQ 的关键条款都有官方链接。
- [ ] “推荐哪天”写明是规划判断；旧说法都已标注。

## 10. 旅行短句

### 目标字段

`phrases.json` 的 `sections[]`：`id`、`title`、`items[]`（`{native, local, note}`）。朗读语言在 `trip.json` 的 `speech.language`（BCP-47，如 `en-US`、`ja-JP`），`speech.label` 是显示名。

### 步骤

1. **按场景分组**：沟通兜底、餐厅、点饮品、交通/打车、酒店、购物、问路、紧急情况、健康/过敏、拍照请人帮忙。
2. **每句写成当地人真的会听懂的说法**，优先短句、礼貌、可直接指着屏幕给对方看。
3. **写当地含义。** 当地特有的点单用语、称呼、习惯（小费、服务费、排队规矩），在 `note` 里解释——特别是字面意思和实际意思不同的说法。
4. **核对语音。** 设定正确的 `speech.language`，在模拟器或真机上播放几句，确认口音和读法可以接受；当地语言有多个变体时选目的地常用的那个。
5. **不写敏感内容。** 不放任何个人信息，不写需要证件号的句子。

### 常见坑

- 直接机翻长句，现场说不出口。
- 当地点单用语（例如饮品、配料的当地简称）只写了字面翻译，没有解释。
- `speech.language` 设错，朗读变成另一种口音或读不出来。

### 完成标准

- [ ] 至少覆盖沟通兜底、餐厅、交通、紧急情况四类。
- [ ] 当地特有用语都有 `note`。
- [ ] 在设备上试播过，语言设置正确。

## 11. 路线与地图

### 背景：一个必须尽早验证的坑

在中国大陆的网络与账号环境下，iOS 的 MapKit 对部分境外地区可能**无法返回路线**（`MKDirections` 报 `OUT_OF_COVERAGE` / 搜索失败），地点搜索也可能报错；而对国内的对照路线正常。这意味着“到了当地大概就好了”不可验证，出发前就用不了。实战项目里这是在功能做完之后才发现的。

**对策：**

- **开工第一周就在目标环境里验证**：用两个真实的目的地坐标请求一次步行路线，同时用一条国内路线做对照。失败就立即改方案。
- **坐标打包进 App**（`locations.json`），不依赖出行时的在线地理编码。
- **可选：自建路线服务。** 模板的 `server/` 提供基于 Valhalla 的路线服务和基于 OpenStreetMap 的地点索引：
  - 路网：从 BBBike 或 Geofabrik 下载目的地区域的 OSM 提取（`.pbf`），构建 Valhalla 瓦片。
  - 行政边界：用包含完整国界的区域提取构建，确保国界过滤和行车方向（左/右行）正确。
  - 地点索引：`scripts/build_route_places.py` 从 OSM 提取生成，按国界过滤，只保留目的地记录。
  - 数据来源、快照日期、校验和、许可证写进产物的来源文件，App 保留 OSM 署名。
  - 路网是静态快照，不含实时交通。
- 不部署后端时，App 仍可离线使用，只是没有逐段路线；地图交给系统地图应用导航。

### 路线呈现的规则

- **不画假直线。** 算不出路线的路段就显示失败，不用两点连线冒充路线。
- **坐标吸附有上限。** 起终点吸附到路网的距离限制在约 100 米内，超出就报失败，提示用户核对入口。
- **部分结果要标明。** 部分路段失败时，显示“已计算部分”，失败路段不计成 0 距离、0 分钟。
- **缺坐标的站点保留在列表里**，只中断相邻路段。
- **实测样本不是承诺。** 调研记录里可以写“某两点步行约 1.2 公里、约 15 分钟，请求约 0.5 秒”，但这只是样本，不是性能或时间承诺。
- **大型建筑中心可能无法步行到达**（坐标在建筑内部），保留失败状态，让用户核对入口或切换交通方式。

### 英文地址复制

打车软件、地图应用通常用英文地址搜索效果最好。模板支持从路线站点复制英文地址。调研时：

- `locations.json` 的 `name`、`address` 写英文（或当地通用拼写），保留分店名、楼层单元号、邮编，去掉重复片段。
- `trip.json` 的 `destination.addressSuffix` 和 `postcodePattern` 用于规范化地址结尾。
- **抽查**：挑 3 个地址（一个地标、一个带单元号的小店、一家酒店），粘贴到 Google Maps 网页版搜索，确认第一条结果就是目标地点。结果写进调研记录。不要宣称“所有地图和打车软件都能准确识别”，也不代表上车点正确。

### 完成标准

- [ ] 已在目标环境验证系统地图的路线能力，结论写进调研记录。
- [ ] 所有可确定的地点都有打包坐标；自建服务（如使用）的数据来源、快照日期、许可证齐全。
- [ ] 英文地址抽查至少 3 个，结果有记录。
- [ ] 界面不会出现假直线或把失败算成 0。

## 12. 汇率

### 目标字段

`trip.json` 的 `currency`：`local`、`home`（ISO 4217 代码）、`localSymbol`、`homeSymbol`、`homePerLocal`（1 单位当地币 = 多少出发地币）、`rateDate`、`rateSource`（`https`）。

### 步骤

1. 选一个公开、可访问、带更新时间的汇率来源（央行、公开汇率 API 等），记录：数值、来源 URL、来源给出的更新时间（带时区）。
2. 备用来源如果显示的日期比当天旧，**不要**把它当成当天汇率。
3. `rateDate` 写采集日期，`rateSource` 写具体链接。
4. 在界面和文案里说明：这是规划参考汇率，与银行实际结算、手续费、动态货币转换无关。

### 常见坑

- 用一个几天前的汇率当“今天”。
- 把银行卡实际扣款金额和规划换算混为一谈。
- 汇率方向写反（`homePerLocal` 是“1 当地币 = ? 出发地币”）。

### 完成标准

- [ ] `homePerLocal`、`rateDate`、`rateSource` 齐全，来源有更新时间。
- [ ] 文案注明“规划参考”。

## 13. 参考信息

`references.json` 的 `references[]`：`{id, title, body, links}`。放不属于某个地点、但旅途中常用的信息：交通卡与乘车方式、紧急电话、当地常见规定（禁带物品、禁烟区域、垃圾分类等）、气候。

- 紧急电话、当地规定必须有政府或官方来源链接。
- 气候只写官方气象机构的气候均值，并说明“气候均值不能预测旅行当天的天气”。
- 安全提示取自本国外交部门或目的地官方；本方案自己的建议（例如“建议 22 点前返回酒店”）要写明是建议，不是当地规定。

## 14. 工具与技巧

### 14.1 读网页：浏览器自动化

- 用能渲染 JavaScript 的真实浏览器（agent 的浏览器工具、Playwright 等）读官网；命令行 `curl` 只适合静态页面和 API。
- 读动态页面的套路：打开 → 等内容加载 → 点开日历/折叠项/标签页 → 读可见文本 → 截图存证（证据放在不进 git 的 `test-results/` 或调研证据目录）。
- 需要登录的平台（小红书、预订平台），由用户在浏览器里自己登录；agent 只读。不保存 Cookie、账号信息到仓库。
- 遇到验证码或机器人检测：停下，请用户手动处理或放弃该来源，**不要尝试绕过**。
- 一次会话打开大量页面时放慢节奏，下载图片时每个请求间隔几秒，并带明确的 User-Agent。

### 14.2 操作原生 App：Computer Use

有些工作只能在原生应用里做，例如在 Apple Maps 里整理一份目的地指南（收藏清单），方便旅途中查看。

- 逐项搜索、添加，**按名称和地址选择**，不要把搜索结果第一条直接加进去——结果里常混有同名的境外地点、停车场、旅行社、中英文重复条目。
- 以地址去重：同一地点的中文名条目和英文名条目只留一个。
- **应用可能中途崩溃。** 重新打开后先重新数一遍已保存的数量，再继续；不要按“我记得加到了第几个”继续。
- 收尾时从头滚到尾读一遍完整列表，去重后核对总数与界面显示一致。
- 删除操作只针对用户明确要求的条目；地图上的“永久关闭”标签只是当时的地图状态，不等于官方公告。
- 记录操作快照：最终清单、数量口径（原有几项、新增几项、删除几项）、搜索时的取舍。

### 14.3 怎么搜才有效

- **官网优先。** 先找到运营方官网，再在官网内找信息；不要从聚合站开始。
- **`site:` 查询。** `site:官网域名 opening hours`、`site:官网域名 filetype:pdf menu`、`site:政府域名 关键词`。
- **多语言、多名称。** 同时用中文名、英文名、当地语言名、旧名搜索；很多地点的中文名有多种写法。
- **英文名往往更准。** 官方页面通常以英文或当地语言为主，用英文名能直接命中官网。
- **看日期。** 每个结果都看页面日期；搜索引擎排在前面的可能是多年前的旧页。
- **官方新闻与公告。** 关闭、维修、搬迁、涨价通常先出现在官方新闻/公告页，而不是主页面。
- **存档对照。** 页面疑似改版时，可以用网页存档服务查看旧版本，理解变化；但存档只用于理解，不作为当前事实的来源。
- **预约系统从官网进。** 餐厅、景点的预约系统入口必须是官网上链接过去的那个，避免进到第三方代订页面。

### 14.4 调研记录

- 每次调研一份记录：`docs/research/YYYY-MM-DD-主题.md`，从 [research-record.md](../templates/research-record.md) 复制。
- 来源表逐行写：URL、读取时间、结论、置信度（高/中/低）。
- 冲突与未决事项单独一节，后续调研优先处理。
- 写明这次改了哪些 `content` 文件和字段，便于审阅 diff。
- 截图、PDF 等原始证据放在不进 git 的目录，记录里只写文件名。
- 不贴私人订单、账号、个人信息。

### 14.5 给 AI agent 的任务写法

把任务交给 agent 时，写清楚这些，能省很多返工：

- 目的地、日期、人数、作息、航班时刻（或“未定”）。
- 要调研的内容类型和目标数量（例如“每个地点 3 张照片、3 篇参考帖”）。
- 必须遵守的规则：本手册第 1 节；只读不写；不提交表单；不发消息。
- 交付物：修改的 `content/*.json`、调研记录、`verify_content.py` 输出。
- 验收标准：`verify_content.py --require-complete` 通过，或列出每一条失败的原因。
