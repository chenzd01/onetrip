# 经验与教训

这个模板来自一次真实旅行的实战项目：一个原生 iOS App，可选的共享后端，内容由人和 AI agent 一起调研。下面是那次项目里真正踩过的坑，已经去掉具体的人、地点和日期，只保留可复用的部分。

每一条都按“现象 → 原因 → 做法”写。标了“模板已落实”的，表示模板的代码或配置已经按这个教训处理过；没标的，是需要你在自己的项目里注意的流程。

内容调研方面的规则见 [research-playbook.md](research-playbook.md)，发布流程见 [ios-delivery.md](ios-delivery.md)。

---

## 一、工程与平台

### 1. 在国内用 MapKit 查境外路线，可能直接失败

- **现象**：功能做完后做真实验收，目的地两个景点之间的步行路线在模拟器上请求失败，报 `MKDirectionsErrorCode=8`（`OUT_OF_COVERAGE`）；地点搜索也报 `MKErrorDomain` 错误。换成新式 API、换新模拟器、把模拟器地区和定位都改成目的地，结果一样；同时一条国内对照路线正常返回。
- **原因**：MapKit 的路线和搜索能力受地区与网络环境影响，在国内环境下对部分境外地区不可用。这无法通过改代码解决，也无法证明“到了当地就一定能用”。
- **做法**：
  - 开工第一周就在真实环境里测一次目的地路线 + 一次国内对照路线。
  - 坐标打包进 App，不依赖出行时在线地理编码。
  - 需要逐段路线时，自建 Valhalla + OpenStreetMap 路网服务。
  - 不画假直线；失败就显示失败。
- **模板已落实**：`content/locations.json` 打包坐标；`server/route_engine.py` / `route_places.py` 提供可选的自建路线和地点搜索；实时区域路线测试是单独开启的验收项（`TRIP_LIVE_ROUTES=1`），常规测试里跳过它，但不把跳过记成通过。

### 2. XcodeGen 用空 Team 生成工程，会悄悄改掉签名配置

- **现象**：准备发布时，发布流程发现生成的工程用的是模拟器开发用的空 Team 配置，差点用错误的签名配置发布。
- **原因**：Xcode 工程由 `project.yml` 生成。机器上 `Signing.xcconfig` 的 Team 为空（模拟器开发时常见）时重新生成，工程里的签名设置就跟着变了；如果工程文件还提交在仓库里，这种变化会混进提交。
- **做法**：
  - Team ID、Bundle ID 只放在不提交的 `ios/Signing.xcconfig` 里。
  - 发布前确认 `Signing.xcconfig` 里是正式 Team，再重新 `xcodegen generate`。
  - 发布检查里核对归档的 Team 和 App Group。
- **模板已落实**：`.xcodeproj` 不提交（`.gitignore` 忽略 `ios/*.xcodeproj/`），因为它会记录 Team ID；签名全部来自 `ios/Signing.xcconfig`，`ExportOptions-TestFlight.plist` 里不写 `teamID`。

### 3. 外部 TestFlight 审核员占用了配对名额

- **现象**：两人配对功能（“碰一下”）第一次真机使用时，第二部手机绑定一直失败。排查服务端数据才发现：构建分发后十几分钟，一台来自境外、系统版本异常新的设备先完成了绑定，占掉了第一个名额。那是 Apple 的外部 Beta 审核员在运行真实的发布包。
- **原因**：最初的绑定是“先到先得两个名额”，没有身份校验。任何拿到同一个发布包的人都能占用，而外部测试每次提审都会有审核员运行真实包。
- **做法**：
  - 第一个名额可以直接绑定；第二个名额只能通过已绑定手机生成的**邀请码**加入，并由已绑定手机确认。
  - 保留一个运维命令，在名额被误占时只重置互动身份表，不碰行程数据。
  - 给审核员准备独立的演示数据库和演示账号，与真实数据隔离。
- **模板已落实**：邀请码配对流程（`server/touch_service.py`）；`python3 server/trip_server.py reset-touch` 只重置互动身份；审核会话（`review.` 前缀）路由到独立的审核数据库，失效的审核凭证不会回落到真实数据。

### 4. 把所有 409 都当成“行程冲突”，真实错误被吞了

- **现象**：绑定被拒时，用户看到的是“暂时没连上”这种通用文案，完全不知道是名额被占。
- **原因**：客户端把任何 HTTP 409 都按“行程保存冲突”解码；互动接口的 409 响应里没有 `latest` 字段，解码失败，被归入通用错误。另外，输入邀请码后状态显示成“已绑定”，实际上还在等对方确认。
- **做法**：
  - 按接口和响应内容区分错误：只有能解出 `latest` 的 409 才是行程冲突。
  - 错误文案要说出真实原因和下一步（“名额已被占用，请用邀请码加入”）。
  - 中间状态如实显示（“等对方确认”），不提前显示成功。
- **模板已落实**：`TripAPI` 只把带 `latest` 的 409 当作行程冲突；绑定被拒时自动展开邀请码入口。

### 5. App 自己压掉了前台通知，节流又把事件丢了

- **现象**：两人互发“碰一下”，都说收不到通知。服务端日志显示推送 APNs 全部返回成功，其中一条用户后来在通知中心里找到了。
- **原因**：两个问题叠加。
  1. 测试时两台手机都在前台，App 的 `willPresent` 对互动推送返回空选项，主动压掉了系统横幅和声音，只播放一个 22 pt 小圆点的动画——两台手机同时拿在手里时几乎看不见。
  2. 服务端对同一接收人 60 秒只排一条推送，连续的几下根本没有进入推送队列。
- **做法**：
  - 前台收到互动时，请求系统横幅、通知中心和声音；系统横幅不可用时，App 内显示一张明显的卡片。
  - 取消单接收人冷却，改为每个事件单独入队，只保留每个发送者每分钟的上限。
  - 发送回执如实说明状态：已被 APNs 接受、被限流不会响、未入队……
- **模板已落实**：`TouchNotifications.swift` 的前台呈现策略；`server/touch_push.py` 按事件入队、明确拒绝时有限次重试、不确定时不重复发送。

### 6. 几乎没有日志，排查只能靠反推

- **现象**：上面两个故障，排查时推送 worker 从启动起一行日志都没写；HTTP 服务只记录方法、路径和状态码。所有结论都是从生产数据库状态和反向代理日志反推出来的。
- **做法**：
  - 服务端对关键决策写结构化日志：绑定、邀请、加入、确认、发送，每条带成员短 ID、决策结果（如 `alert=queued | no-token | throttled`）；被拒请求记录状态码和原因。
  - 推送 worker 记录每次投递的返回 ID、状态码、原因和耗时。
  - 设备令牌、身份凭证只以哈希前几位出现，不记录原文和私人内容。
  - App 内提供诊断记录页（可查看、可复制），指纹口径与服务端一致，方便用户把记录发给你。
- **模板已落实**：`TouchDiagnostics.swift` 与服务端结构化日志。

### 7. 导出时磁盘满了

- **现象**：第一次导出上传时失败，报 “No space left on device”。
- **原因**：模拟器、DerivedData、多次归档占满了内置磁盘。
- **做法**：
  - 构建产物（DerivedData、归档、测试结果）放到空间充足的外置磁盘，原路径用符号链接指过去；外置盘要保持挂载，不要移动正在使用的构建目录。
  - 只清理本任务生成的产物（本任务建的模拟器、失败的暂存目录），不要删别的项目或个人文件。
  - 发布前用 `df -h` 看一眼剩余空间。

### 8. 上传最后一段特别慢

- **现象**：导出上传时进度长时间卡在最后一段；有一次在接近完成时被手动停止，没有得到成功回执。
- **做法**：
  - 上传前确认网络稳定，给上传留足时间，不要在截止时间前才上传。
  - 以 `xcodebuild` 输出的 `Upload succeeded` / `EXPORT SUCCEEDED` 和退出码 0 为准。没有回执就是没有上传成功，要重新上传（构建号按规则处理，见 ios-delivery.md）。
  - 慢的上传可以断开重连后重试，但不要同时跑两个上传。

### 9. App Store Connect 会话中途过期

- **现象**：上传后在浏览器里等构建处理，会话过期跳回登录页，分组分发没做完。
- **做法**：
  - 分发前确认登录状态；过期了由用户自己重新登录。
  - 记录里写“最后确认的状态是处理中”，不要写成“已分发”。
  - 恢复登录后逐个打开测试组的 Builds 页面核对，再记录结果。

### 10. 全新模拟器里的地图首次启动引导挡住了跳转

- **现象**：从 App 跳转到系统地图查看目的地，全新模拟器上地图 App 先弹出首次启动引导和定位权限，目的地没有显示；完成引导后再跳一次，图钉正确。
- **做法**：验收“跳转到地图”前，先在该模拟器上手动打开一次地图 App 完成引导；截图作为证据时说明这一点。

### 11. SQLite 只读 URI 少写了 `file:`，生成了一个奇怪的文件

- **现象**：部署预检时以只读方式打开生产数据库，结果在数据目录里多出一个 0 字节文件，文件名就是 `trip.sqlite3?mode=ro`。
- **原因**：Python `sqlite3.connect(..., uri=True)` 需要 `file:` 前缀才会把 `?mode=ro` 当参数；少了前缀，整个字符串被当成文件名，并且以读写方式新建了文件。
- **做法**：
  - 只读打开写成 `sqlite3.connect('file:/path/to/db.sqlite3?mode=ro', uri=True)`。
  - 预检脚本执行后检查数据目录有没有多出文件；多出来的空文件确认为空后再删。
  - 预检永远不能写生产数据。

### 12. 内容更新差点覆盖用户自己的编辑

- **现象**：内容调研修正了默认行程后，如果直接替换，用户在 App 里排好的行程和勾选会被冲掉。
- **做法**：
  - 打包内容只作为“没有本机工作区时”的默认值。
  - 第一次编辑时把当时的起点冻结为合并基线；后续打包的新默认值不会改变“用户改过哪些字段”的判断。
  - 本机存档遇到不认识的字段或未来版本时拒绝覆盖（fail closed），不改写文件。
  - 升级必须保持 Bundle ID、App Group、钥匙串服务名和工作区路径不变；提醒测试者“原地更新，不要卸载”。
- **模板已落实**：`UpgradePersistenceTests` 覆盖默认值变化、升级后首次同步、新增与有意删除、保存失败、未知字段保护。

### 13. 测试不能碰生产

- 集成测试只接受回环地址（`127.0.0.1`）的一次性隔离数据库，否则跳过（`TRIP_INTEGRATION_URL`）。
- 永远不要把会写数据的测试指向真实服务，也不要把生产数据库或凭证提交进仓库。
- 部署前后比对共享数据的指纹（行程、修订历史、设置、附件），确认没有被改动。

## 二、诚实报告规则

这一节是那次项目最重要的收获：很多“已完成”其实只是完成了一半。下面每一对概念都不能混用，记录里要分开写。

| 不要把 | 当成 | 原因 |
| --- | --- | --- |
| 模拟器上正常 | 真机上正常 | 通知、触感、锁屏、专注模式、性能、第三方 App 跳转都只能真机验证 |
| 上传成功 | Apple 处理完成 | 上传只说明包提交了 |
| 处理完成 | 测试者可以测试 | 外部组可能还要 Beta 审核，还要加入分组 |
| 测试组显示 Testing | 手机已安装 | 测试者页面的“已安装版本”才是安装证据，而且可能还是旧版本 |
| 通知已发出 | 对方收到通知 | 测试者可能没打开邮件或 TestFlight |
| APNs 接受了推送 | 手机响了 / 对方看到了 | 系统仍会按权限、专注模式、通知摘要决定是否展示 |
| 测试被跳过 | 测试通过 | 需要外部环境的测试跳过时，要写“跳过 N 项”，不计入通过 |
| 发出了跳转请求 | 在目标 App 里打开成功 | URL 能分发不代表目标 App 正确打开了对应页面 |
| 服务健康检查正常 | 功能正常 | healthz 只说明进程活着 |
| 旧的验收记录 | 今天的实时状态 | 发布前必须重新读取生产基线，不能拿昨天的回执代替 |

写测试结果时要写**精确数字**：“原生 141 项通过、7 项跳过（依赖隔离 HTTP 服务等，本次未启动）、0 失败”，而不是“测试都过了”。

未验证的部分要单独列出来，放在“未证明的边界”里（见 [release-record.md](../templates/release-record.md)）。

## 三、流程

### 1. 只读调研，不做不可逆操作

酒店查价停在填写入住人信息页、餐厅查位停在选择时段、不提交表单、不发邮件、不领券、不接受协议。需要联系第三方时起草文本交给用户。这条规则让 agent 可以放心地大量查询。

### 2. 发布要窄

- 每次发布只包含本次改动的文件，用白名单限定；发布前核对生产上的旧文件和预期基线逐字节一致，防止覆盖别人的并行更新。
- 先备份（数据库用 SQLite 的备份 API 做一致快照），再安装，最后比对数据指纹和健康检查。
- 回滚只恢复本次代码，**不要用旧的整库备份覆盖更新过的数据**。

### 3. 两阶段启用新的共享数据类型

新增一种共享数据（例如路线里的英文地址记录）时：

1. 先部署能读写新类型的服务端，服务端开关保持关闭；分发能读取新类型的 App。
2. **确认两部手机都已安装兼容版本**后，再打开服务端开关。
3. 关闭开关只阻止新增和修改，保留已有记录。

TestFlight 显示“可测试”或“已通知”都不是安装证明。

### 4. 每个构建留一份发布记录

记录变更范围、精确测试数、后端是否发布、归档与上传回执、TestFlight 状态、未证明的边界。模板见 [release-record.md](../templates/release-record.md)。记录里不要写密钥、证书、个人路径和私人信息。

### 5. 冲突和缺口写下来

调研里的来源冲突、没查到的价格、没找到合适照片的地点，都写进调研记录。下一轮调研优先处理这些，而不是重新从头查。

## 四、产品

### 1. 内容离线放在 App 里

旅途中网络不可靠（入境前后、地铁里、山里）。地点、攻略、准备清单、短句、参考帖摘要全部打包进 App，离线可读；共享服务只同步用户自己的编辑。

### 2. “今日”页按日期显示行前准备

- 行前准备只在“今天及以前到期、仍未完成”的事项存在时显示在“今日”页；`dueDate` 为空的事项立即显示。
- 未来才到期的事项（例如返程前一晚复查）不提前打扰。
- 进度仍按全部事项计算。
- 今日页完整显示当天行程（按原顺序，包括已结束和时间待定的事项），不要按当前时间截断——截断会让用户以为当天安排结束了，而返程航班其实还没起飞。

### 3. 把不确定性展示出来

- 需要预约、部分关闭、价格未确认、条件优惠，用颜色 + 图标 + 文字同时标出。
- 订位情况永远写成“查询时显示……”，带查询时间。
- 推荐不等于有位；加入行程不等于订好。

### 4. 不要自动改写用户保存的行程

- 内容更新、日期跨天、默认值变化，都不能自动替换用户的编辑。
- 删除一个已预订的餐食或移到别的日子时，明确提示影响；App 内的操作不会取消或修改真实订单，也要说清楚。
- 删除行程卡片不删除已经保存的票据。

### 5. 小交互要真的看得见

互动功能最初的反馈只是一个很小的圆点动画，真实使用时两个人都没注意到。反馈要足够明显，并且在系统通知被压制时有兜底卡片。

### 6. 无障碍与大字号

最大辅助字号下会暴露文字重叠、日期控件截断、按钮挤在一行的问题。每个新界面都在最大字号和深色模式下看一遍；地图标记的可点击区域不小于 44 pt。VoiceOver 的实际朗读顺序需要真机验证，不要只看标签是否存在。
