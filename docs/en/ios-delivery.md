# iOS build and TestFlight release

This document explains how to build the template, once filled with content, into an app and ship it to your travel companions through TestFlight. The process comes from a real trip project. For pitfalls we hit see [lessons-learned.md](lessons-learned.md); for the per-release record template see [release-record.md](../templates/release-record.md).

> Every `<...>` in this document is a placeholder. Commands are run from the repository root by default. Never put Team IDs, certificates, APNs keys, shared access keys or personal paths in the repository or in release records.

---

## 1. Prerequisites

| Need | Notes |
| --- | --- |
| macOS + Xcode 26 or later | The project's minimum deployment target is iOS 26.0, iPhone only |
| XcodeGen | `brew install xcodegen` |
| Python 3 + Pillow | Generates bundled resources and processes images: `python3 -m pip install Pillow` |
| A paid Apple Developer account | Not needed for simulator development; required for real-device installs and TestFlight |
| Enough disk space | Archives, DerivedData and simulators take a lot of space; reserve 20 GB or more; when space is tight, put build artifacts on an external disk (see lessons-learned.md) |

## 2. The project is generated

The repository **does not commit** the `.xcodeproj`. The project is defined in `ios/project.yml` and generated by XcodeGen. Reason: the generated project records the Team ID; if the project file is committed, signing differences between machines leak into commits, and it may be rewritten under an empty Team (see Section I, item 2 of lessons-learned.md).

After every pull, after adding or removing Swift files, and after editing `project.yml`, regenerate in this order:

```sh
# 1. Validate content (structure gate)
python3 scripts/verify_content.py

# 2. Generate the app's bundled resources and ios/Generated.xcconfig from content/
python3 scripts/build_ios_resources.py

# 3. Confirm generated output is up to date
python3 scripts/verify_content.py --built-catalog

# 4. Generate the Xcode project (outputs ios/TripJournal.xcodeproj)
xcodegen generate --spec ios/project.yml
```

`build_ios_resources.py` must run before `xcodegen`, because `project.yml` references `ios/TripJournal/Resources/Content/` as a resource directory; if the directory doesn't exist, the project will be missing resources. It also writes `ios/Generated.xcconfig` (app display name) from `content/trip.json`.

## 3. Signing configuration

### 3.1 `ios/Signing.xcconfig`

Copy it from the example; this file is not committed:

```sh
cp ios/Signing.example.xcconfig ios/Signing.xcconfig
```

| Key | Value |
| --- | --- |
| `DEVELOPMENT_TEAM` | Your paid Team ID. Can be left empty if you only run the simulator; required for real devices and archiving |
| `APP_BUNDLE_ID` | A reverse domain you own, e.g. `com.<your-domain>.<app-name>` |

Derived from `APP_BUNDLE_ID`:

| Purpose | Identifier |
| --- | --- |
| App | `<APP_BUNDLE_ID>` |
| Widget extension | `<APP_BUNDLE_ID>.widgets` |
| App Group (data shared between app and widget) | `group.<APP_BUNDLE_ID>` |
| Unit tests | `<APP_BUNDLE_ID>.tests` |

The configuration load order is defined in `ios/App.xcconfig`: defaults first, then `Generated.xcconfig`, `Signing.xcconfig` (required), `SharedAccess.xcconfig` (optional).

### 3.2 Register in the Apple Developer portal

1. Register the App ID `<APP_BUNDLE_ID>` with App Groups enabled.
2. Register the App ID `<APP_BUNDLE_ID>.widgets` with App Groups enabled.
3. Register the App Group `group.<APP_BUNDLE_ID>` and assign it to both App IDs above.
4. Push Notifications capability:
   - The template's `TripJournal.entitlements` includes `aps-environment`, whose value comes from the build setting `APNS_ENVIRONMENT` (`development` for Debug, `production` for Release).
   - With automatic signing plus `-allowProvisioningUpdates`, Xcode requests the matching capabilities for the App ID based on the entitlements.
   - You only need an APNs signing key (`.p8`) if you deploy the backend and use the "nudge" interaction. An APNs key and an App Store Connect API key are different things and are not interchangeable. Keep the key outside the repository, readable only by the push worker's account.
   - If you don't deploy a backend at all, the app works offline; just keep the profile and entitlements consistent.

After release, never change the Bundle ID, App Group, Keychain service name or workspace path, or testers will lose their local data when they update in place.

### 3.3 Optional: `ios/SharedAccess.xcconfig`

Only needed if you deploy the `server/` backend. Copy it from `ios/SharedAccess.example.xcconfig` and fill in:

- `TRIP_SERVER_URL`: the backend URL. Note that `//` starts a comment in xcconfig, so write it as `https:/$()/<your-domain>/onetrip/<random-path>/`.
- `TRIP_SHARED_ACCESS_KEY`: 32–256 random characters; the server stores only its SHA-256 (environment variable `TRIP_NATIVE_KEY_SHA256`).

This key is compiled into the app, and anyone who gets the install package can access the same shared plan, so it is an "install-level" access capability, not a personal identity. Don't commit it, and don't put it in release records.

## 4. Local development and testing

```sh
# List available simulators
xcrun simctl list devices available

# Build and run tests (replace <simulator-name> with an iPhone simulator from the list above)
xcodebuild test \
  -project ios/TripJournal.xcodeproj -scheme TripJournal \
  -destination 'platform=iOS Simulator,name=<simulator-name>'
```

- Keep the default ad-hoc signing when running on the simulator so the Keychain works properly; don't use `CODE_SIGNING_ALLOWED=NO` for runtime verification.
- Real HTTP integration tests need a throwaway, isolated local server, with `TRIP_INTEGRATION_URL=http://127.0.0.1:<port>/` set in the test run environment; only loopback addresses are accepted, otherwise the tests are skipped. Never point them at production.
- The online acceptance test for regional routes needs `TRIP_LIVE_ROUTES=1` and is skipped in regular runs.
- Skipped tests must be counted separately and never counted as passes.

Content-related Python tests:

```sh
python3 scripts/test_ios_resources.py
python3 -m unittest discover -s server -p 'test_*.py'     # when using the backend
python3 -m unittest discover -s deploy -p 'test_*.py'     # when using the deployment scripts
```

## 5. Version numbers

Version numbers live in `settings.base` at the top level of `ios/project.yml`:

```yaml
MARKETING_VERSION: '1.0.0'       # version users see
CURRENT_PROJECT_VERSION: '1'     # build number
```

- The app and widget share both values, so they stay in sync naturally. App Store Connect rejects mismatched app and extension versions.
- `ios/ExportOptions-TestFlight.plist` sets `manageAppVersionAndBuildNumber = false`, so export doesn't change the build number automatically.
- **Increment `CURRENT_PROJECT_VERSION` by 1 before every upload.** Within the same marketing version, a build number Apple has already accepted can't be reused; when an upload's outcome is uncertain, just use a new number to save yourself the investigation.
- Rerun `xcodegen generate` after updating version numbers.

## 6. Pre-release checks

Run these on a clean main branch before every archive, and write the exact results into the release record:

- [ ] `python3 scripts/verify_content.py --require-complete` passes (real trip).
- [ ] `python3 scripts/build_ios_resources.py` succeeds and `python3 scripts/verify_content.py --built-catalog` passes.
- [ ] `ios/Signing.xcconfig` has the real Team and real Bundle ID (not the empty Team used for the simulator), then rerun `xcodegen generate`.
- [ ] Native tests: record the exact pass, skip and fail counts, and the reasons for skips.
- [ ] When using the backend: exact counts for the server and deployment script tests.
- [ ] `git status` is clean and the release source is committed.
- [ ] If the repository is public: `python3 scripts/privacy_check.py` finds nothing (it scans for keys, personal paths, public IPs, email addresses, and private strings you listed yourself in `.privacy-denylist`).
- [ ] Enough free disk space (`df -h`).

## 7. Archive and upload

### 7.1 Archive

```sh
BUILD=<build-number>
xcodebuild -project ios/TripJournal.xcodeproj -scheme TripJournal \
  -configuration Release -destination 'generic/platform=iOS' \
  -archivePath "ios/build/TripJournal-$BUILD.xcarchive" \
  -allowProvisioningUpdates archive
```

`-allowProvisioningUpdates` lets Xcode create or update provisioning profiles automatically using the Apple account signed in on this machine.

### 7.2 Archive checks

```sh
APP="ios/build/TripJournal-$BUILD.xcarchive/Products/Applications/TripJournal.app"
WIDGET="$APP/PlugIns/TripWidgets.appex"

# Signature integrity
codesign --verify --deep --strict --verbose=2 "$APP"
codesign --verify --deep --strict --verbose=2 "$WIDGET"

# Version numbers: app and widget must match
/usr/libexec/PlistBuddy -c 'Print CFBundleShortVersionString' -c 'Print CFBundleVersion' "$APP/Info.plist"
/usr/libexec/PlistBuddy -c 'Print CFBundleShortVersionString' -c 'Print CFBundleVersion' "$WIDGET/Info.plist"

# Bundle ID, Team, App Group
codesign -d --entitlements :- "$APP"
codesign -d --entitlements :- "$WIDGET"

# Bundled resources match the generated directory file by file (no output means identical)
diff -rq ios/TripJournal/Resources/Content "$APP/Content"
```

Verify:

- The app and widget have the same marketing version and build number, and they are the numbers you intend to ship.
- The Team prefix and `application-groups` in the entitlements are the real values.
- `Content/` matches the generated directory (its `manifest.json` records each file's length and SHA-256).

### 7.3 Upload

```sh
xcodebuild -exportArchive \
  -archivePath "ios/build/TripJournal-$BUILD.xcarchive" \
  -exportOptionsPlist ios/ExportOptions-TestFlight.plist \
  -exportPath "ios/build/upload-$BUILD" \
  -allowProvisioningUpdates
```

- The `destination` in `ExportOptions-TestFlight.plist` is `upload`, so this command uploads straight to App Store Connect. Run it only on an archive that passed the checks.
- The plist has **no `teamID`**; the signing Team comes from `Signing.xcconfig` and the account signed in on this machine, so the file is safe to commit.
- Signs of success: the output contains `Upload succeeded` and `EXPORT SUCCEEDED`, and the exit code is 0. Save this output to a local log (not in git).
- If the upload is very slow or drops midway: no success receipt means it wasn't uploaded; archive and upload again with a new build number. Never run two uploads in parallel.

### 7.4 Check the production entitlements of the distribution package

The archive itself is usually development-signed, so its `aps-environment` is not evidence for production. To confirm the entitlements after distribution signing, export a separate IPA (without uploading):

```sh
cp ios/ExportOptions-TestFlight.plist "ios/build/ExportOptions-IPA-$BUILD.plist"
plutil -replace destination -string export "ios/build/ExportOptions-IPA-$BUILD.plist"
xcodebuild -exportArchive \
  -archivePath "ios/build/TripJournal-$BUILD.xcarchive" \
  -exportOptionsPlist "ios/build/ExportOptions-IPA-$BUILD.plist" \
  -exportPath "ios/build/ipa-$BUILD" -allowProvisioningUpdates

cd "ios/build/ipa-$BUILD" && unzip -q -o *.ipa
codesign -d --entitlements :- Payload/TripJournal.app
```

Expected: `aps-environment` is `production` (when using push), `get-task-allow` is `false`, and the Team and App Group are correct.

## 8. App Store Connect and TestFlight

### 8.1 Create the app record (once)

In App Store Connect → "Apps" → New App: platform iOS, name, primary language, Bundle ID (choose the `<APP_BUNDLE_ID>` registered in Section 3.2), SKU (any unique string you choose).

`Info.plist` already declares `ITSAppUsesNonExemptEncryption = false` (only system-provided transport encryption is used), so you don't have to answer the export compliance question after every upload. If you add custom encryption, re-evaluate this.

### 8.2 Test groups

| Type | Who | Review | Good for |
| --- | --- | --- | --- |
| Internal test group | App Store Connect team members (need an account role) | No beta review needed | Installing and accepting it yourself first |
| External test group | Anyone, invited by email (or public link) | The first build of each marketing version needs Beta App Review | Friends traveling with you |

- Create an internal group for your own preview first, and add the build to the external group once it checks out.
- Use **targeted email invitations** for the external group; don't casually open a public link.
- Don't expand anyone's App Store Connect role just to add them as a tester.

### 8.3 First external review submission

Fill in TestFlight → "Test Information":

- Beta app description, feedback email.
- Contact information (name, phone, email) — enter it in App Store Connect, **never in the repository**.
- Review notes (in English): what the app does, whether login is required, where the offline content is, which entry points exist.
- If a demo account is needed: when using the backend, you can use `server/trip_server.py serve --review-db <review-database>` together with the environment variable `TRIP_REVIEW_KEY_SHA256` to put reviewers into a separate demo dataset; generate demo data only from public sample content, with attachments clearly labeled "for demo only". **Never give reviewers your real itinerary or real credentials.**

External reviewers run the real release build. Any feature that "consumes a resource on first open" (such as pairing slots) must assume the reviewer will tap it (see Section I, item 3 of lessons-learned.md).

### 8.4 Distributing each build

After a successful upload:

1. Wait for Apple to finish processing (the build status changes from "Processing" to available).
2. Fill in this update's notes in the build's "What to Test" (Chinese is fine). Every time, include: **"Please update directly in TestFlight; don't uninstall the old version, or your local drafts and tickets will be lost."**
3. Add the build to the internal and external groups, and check **Automatically notify testers** when submitting.
4. Open each test group's Builds page and confirm this build shows **Testing** and an expiration date.

Rules and observations:

- **Only one build per marketing version can be in beta review at a time.** While the previous one is still in review, the next one can only go to the internal group; submit it externally after the previous one passes.
- After the first build of a marketing version passes external review, later builds submitted to the external group often go straight to Testing, but this is not guaranteed; go by the page status.
- Builds expire after 90 days.
- Group requests occasionally fail; refresh the page and retry. If the browser session expires, the user logs in again, and the record states "last confirmed status".

### 8.5 Status ladder

Each rung must be confirmed and recorded on its own; never skip rungs when drawing conclusions:

```text
Archive succeeded
  → Upload succeeded (Upload succeeded / EXPORT SUCCEEDED, exit code 0)
    → Apple finished processing
      → Added to test groups (internal / external)
        → External review passed (if required)
          → Test group Builds page shows Testing
            → Tester page shows "Installed <this build>"
              → Actual acceptance on a real device passed
```

TestFlight showing "Notified" doesn't mean the tester received it; the installed version shown on the tester page may still be an old build.

## 9. Release record

Write a release record for every build in `docs/releases/` (or wherever you prefer), copied from [release-record.md](../templates/release-record.md). At minimum it includes:

- Scope of changes (what users will notice).
- Local verification: exact test counts (passed / skipped / failed) and reasons for skips.
- Backend: whether it was released; which files were released; whether data fingerprints matched before and after.
- Archive and upload: version numbers, signing check results, upload receipt time.
- TestFlight: processing status, groups added, whether review was needed, status confirmed on the page.
- Unproven boundaries: parts not yet verified, such as real devices, notification delivery and installation status.
- Artifact locations: only paths relative to the repository or "local artifacts directory"; never personal absolute paths.

**Never put in the record**: Team ID, App Store Connect internal IDs, build UUIDs, certificates and keys, shared access keys, server addresses and paths, tester emails and phone numbers, personal computer paths.

## 10. Optional: backend

The template's `server/` provides shared itinerary sync, full-day routes and the "nudge" interaction; `deploy/` provides systemd units, a backup timer and a narrow-scope release script. The app is fully usable offline without a backend.

Principles when deploying the backend (see lessons-learned.md for details):

- Before releasing, take a consistent snapshot with the SQLite backup API (`python3 server/trip_server.py backup --output <backup-file>`) and record fingerprints of the shared data.
- Install only allowlisted files, `--dry-run` first, and verify that the old production files match the expected baseline.
- After releasing, compare data fingerprints and check the health endpoint; a healthy health endpoint doesn't mean the features work.
- Rollback restores only this release's code; never overwrite new data with an old full-database backup.
- Enable new shared data types in two phases: first deploy a server and app that can read them, and only turn on the write switch after confirming every phone has the compatible version installed.
