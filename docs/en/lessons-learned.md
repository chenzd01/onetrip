# Lessons learned

This template comes from a real project built for a trip: a native iOS app, an optional shared backend, and content researched jointly by people and AI agents. Below are the pitfalls we actually hit in that project, with specific people, places and dates removed and only the reusable parts kept.

Each item is written as "symptom → cause → what to do". Items marked "Handled in the template" mean the template's code or configuration already addresses the lesson; unmarked items are process points you need to watch in your own project.

For content research rules see [research-playbook.md](research-playbook.md); for the release process see [ios-delivery.md](ios-delivery.md).

---

## I. Engineering and platform

### 1. Querying routes abroad with MapKit from within mainland China may simply fail

- **Symptom**: during real acceptance testing after the feature was done, a walking route between two sights at the destination failed on the simulator with `MKDirectionsErrorCode=8` (`OUT_OF_COVERAGE`); place search also returned `MKErrorDomain` errors. Switching to the newer API, using a fresh simulator, and setting the simulator's region and location to the destination all gave the same result, while a domestic control route returned normally.
- **Cause**: MapKit's routing and search capabilities depend on region and network environment, and from within mainland China they are unavailable for some regions abroad. This can't be fixed by modifying code, and there's no way to prove it "will definitely work once you're there".
- **What to do**:
  - In the first week of the project, test one destination route + one domestic control route in the real environment.
  - Bundle coordinates into the app; don't rely on online geocoding during the trip.
  - When you need segment-by-segment routes, self-host a Valhalla + OpenStreetMap routing service.
  - Don't draw fake straight lines; if it fails, show that it failed.
- **Handled in the template**: `content/locations.json` bundles coordinates; `server/route_engine.py` / `route_places.py` provide optional self-hosted routing and place search; the live regional route test is a separately enabled acceptance item (`TRIP_LIVE_ROUTES=1`) that is skipped in regular test runs, but a skip is never recorded as a pass.

### 2. XcodeGen with an empty Team silently changes the signing configuration

- **Symptom**: while preparing a release, the release process found that the generated project was using the empty-Team configuration from simulator development, and we nearly shipped with the wrong signing configuration.
- **Cause**: the Xcode project is generated from `project.yml`. If you regenerate while the machine's `Signing.xcconfig` has an empty Team (common during simulator development), the project's signing settings change along with it; if the project file is also committed, the change leaks into commits.
- **What to do**:
  - Keep Team ID and Bundle ID only in the uncommitted `ios/Signing.xcconfig`.
  - Before releasing, confirm that `Signing.xcconfig` has the real Team, then rerun `xcodegen generate`.
  - Verify the archive's Team and App Group as part of the release checks.
- **Handled in the template**: `.xcodeproj` is not committed (`.gitignore` ignores `ios/*.xcodeproj/`) because it records the Team ID; all signing comes from `ios/Signing.xcconfig`, and `ExportOptions-TestFlight.plist` doesn't contain `teamID`.

### 3. An external TestFlight reviewer took a pairing slot

- **Symptom**: the first time the two-person pairing feature ("nudge") was used on real devices, binding the second phone kept failing. Only after inspecting the server data did we find that about ten-plus minutes after the build was distributed, a device from abroad running an unusually new OS version had completed binding first and taken the first slot. It was Apple's external beta reviewer running the real release build.
- **Cause**: the original binding was "first come, first served, two slots" with no identity check. Anyone with the same release build could take a slot, and every external-testing submission has a reviewer running the real build.
- **What to do**:
  - The first slot can bind directly; the second slot can only join via an **invite code** generated by the already-bound phone, and must be confirmed by that phone.
  - Keep an ops command that, when a slot is taken by mistake, resets only the interaction identity table without touching itinerary data.
  - Prepare a separate demo database and demo account for reviewers, isolated from real data.
- **Handled in the template**: invite-code pairing flow (`server/touch_service.py`); `python3 server/trip_server.py reset-touch` resets only interaction identities; review sessions (`review.` prefix) are routed to a separate review database, and an invalid review credential never falls back to real data.

### 4. Treating every 409 as an "itinerary conflict" swallowed the real error

- **Symptom**: when binding was rejected, the user saw a generic message like "couldn't connect right now" and had no idea the slot was taken.
- **Cause**: the client decoded every HTTP 409 as an "itinerary save conflict"; the interaction endpoint's 409 response has no `latest` field, so decoding failed and it was lumped into a generic error. In addition, after entering an invite code the status showed "bound" while it was actually still waiting for the other side to confirm.
- **What to do**:
  - Distinguish errors by endpoint and response content: only a 409 from which `latest` can be decoded is an itinerary conflict.
  - Error messages should state the real cause and the next step ("slot already taken, join with an invite code").
  - Show intermediate states truthfully ("waiting for the other side to confirm"); don't show success early.
- **Handled in the template**: `TripAPI` treats only a 409 carrying `latest` as an itinerary conflict; when binding is rejected, the invite-code entry expands automatically.

### 5. The app suppressed its own foreground notifications, and throttling dropped events

- **Symptom**: the two travelers sent each other "nudges" and both said no notifications arrived. Server logs showed APNs returned success for every push, and the user later found one of them in Notification Center.
- **Cause**: two problems stacked up.
  1. During testing both phones were in the foreground, and the app's `willPresent` returned empty options for interaction pushes, actively suppressing the system banner and sound and only playing a 22 pt dot animation — nearly invisible when both phones are in hand at once.
  2. The server queued only one push per recipient per 60 seconds, so several nudges in a row never made it into the push queue.
- **What to do**:
  - When an interaction arrives in the foreground, request the system banner, Notification Center and sound; when the system banner isn't available, show a prominent in-app card.
  - Remove the per-recipient cooldown; queue every event individually and keep only a per-sender per-minute cap.
  - Delivery receipts should state the status truthfully: accepted by APNs, throttled and won't ring, not queued…
- **Handled in the template**: the foreground presentation policy in `TouchNotifications.swift`; `server/touch_push.py` queues per event, retries a limited number of times on explicit rejection, and does not resend when the outcome is uncertain.

### 6. Almost no logs, so debugging meant reasoning backwards

- **Symptom**: for the two failures above, the push worker hadn't written a single log line since it started; the HTTP service logged only method, path and status code. Every conclusion was reverse-engineered from production database state and reverse proxy logs.
- **What to do**:
  - The server writes structured logs for key decisions: bind, invite, join, confirm, send — each with a short member ID and the decision outcome (e.g. `alert=queued | no-token | throttled`); rejected requests log the status code and reason.
  - The push worker logs the returned ID, status code, reason and duration of every delivery.
  - Device tokens and identity credentials appear only as the first few characters of a hash; raw values and private content are never logged.
  - Provide an in-app diagnostics log screen (viewable, copyable) using the same fingerprint scheme as the server, so users can easily send you the log.
- **Handled in the template**: `TouchDiagnostics.swift` and server-side structured logging.

### 7. The disk filled up during export

- **Symptom**: the first export-and-upload failed with "No space left on device".
- **Cause**: simulators, DerivedData and multiple archives filled the internal disk.
- **What to do**:
  - Put build artifacts (DerivedData, archives, test results) on an external disk with plenty of space and symlink the original paths to it; keep the external disk mounted, and don't move build directories that are in use.
  - Clean up only artifacts generated by the current task (simulators this task created, failed staging directories); don't delete other projects or personal files.
  - Check free space with `df -h` before releasing.

### 8. The last stretch of the upload is especially slow

- **Symptom**: during export-and-upload, progress sat on the last stretch for a long time; once it was manually stopped just before finishing and no success receipt was received.
- **What to do**:
  - Make sure the network is stable before uploading, allow plenty of time, and don't upload right before a deadline.
  - Go by `Upload succeeded` / `EXPORT SUCCEEDED` in the `xcodebuild` output and exit code 0. No receipt means the upload did not succeed and must be redone (handle the build number per the rules, see ios-delivery.md).
  - A slow upload can be disconnected and retried, but never run two uploads at the same time.

### 9. The App Store Connect session expired midway

- **Symptom**: while waiting in the browser for the build to process after upload, the session expired and bounced to the login page, leaving group distribution unfinished.
- **What to do**:
  - Confirm you're logged in before distributing; if the session expires, the user logs in again themselves.
  - In the record, write "last confirmed status was processing", not "distributed".
  - After logging back in, open each test group's Builds page to verify, then record the result.

### 10. The Maps first-launch onboarding on a fresh simulator blocked the hand-off

- **Symptom**: when jumping from the app to the system Maps app to view a destination, on a fresh simulator Maps first showed its first-launch onboarding and location permission prompt, and the destination didn't appear; after completing onboarding and jumping again, the pin was correct.
- **What to do**: before accepting "open in Maps", manually open the Maps app once on that simulator to finish onboarding; mention this when using screenshots as evidence.

### 11. A SQLite read-only URI without `file:` created a strange file

- **Symptom**: a deployment preflight opened the production database read-only, and a 0-byte file literally named `trip.sqlite3?mode=ro` appeared in the data directory.
- **Cause**: Python's `sqlite3.connect(..., uri=True)` needs the `file:` prefix to treat `?mode=ro` as a parameter; without it, the whole string is taken as the file name, and the file is created in read-write mode.
- **What to do**:
  - Open read-only with `sqlite3.connect('file:/path/to/db.sqlite3?mode=ro', uri=True)`.
  - After running the preflight script, check whether any extra files appeared in the data directory; confirm an extra file is empty before deleting it.
  - A preflight must never write production data.

### 12. A content update nearly overwrote the user's own edits

- **Symptom**: after content research corrected the default itinerary, replacing it outright would have wiped out the itinerary and check marks the user had arranged in the app.
- **What to do**:
  - Bundled content is only the default used "when there is no local workspace".
  - On the first edit, freeze the starting point at that moment as the merge baseline; new defaults in later bundles don't change the judgment of "which fields the user changed".
  - When the local save encounters unknown fields or a future version, refuse to overwrite (fail closed) and don't rewrite the file.
  - Upgrades must keep the Bundle ID, App Group, Keychain service name and workspace path unchanged; remind testers to "update in place, don't uninstall".
- **Handled in the template**: `UpgradePersistenceTests` covers default changes, the first sync after an upgrade, additions and intentional deletions, save failures, and unknown-field protection.

### 13. Tests must not touch production

- Integration tests accept only a throwaway, isolated database on the loopback address (`127.0.0.1`), otherwise they are skipped (`TRIP_INTEGRATION_URL`).
- Never point tests that write data at a real service, and never commit production databases or credentials to the repository.
- Compare fingerprints of shared data (itinerary, revision history, settings, attachments) before and after deployment to confirm nothing changed.

## II. Honest reporting rules

This section is the most important takeaway from that project: many "done" items were really only half done. The pairs below must never be conflated, and records must state them separately.

| Don't treat | as | Why |
| --- | --- | --- |
| Works in the simulator | Works on a real device | Notifications, haptics, lock screen, Focus modes, performance and third-party app hand-offs can only be verified on a real device |
| Upload succeeded | Apple finished processing | An upload only means the package was submitted |
| Processing finished | Testers can test | External groups may still need beta review and to be added to the group |
| Test group shows Testing | Installed on the phone | The "installed version" on the tester page is the evidence of installation, and it may still be an old version |
| Notification sent | The other person received it | Testers may not have opened the email or TestFlight |
| APNs accepted the push | The phone rang / the other person saw it | The system still decides whether to display it based on permissions, Focus modes and notification summaries |
| Test skipped | Test passed | When tests that need an external environment are skipped, write "N skipped" and don't count them as passes |
| A hand-off request was sent | It opened successfully in the target app | A URL being dispatched doesn't mean the target app opened the right page |
| Service health check OK | Feature works | healthz only means the process is alive |
| An old acceptance record | Today's live status | Before releasing, re-read the production baseline; yesterday's receipt is no substitute |

When writing test results, give **exact numbers**: "141 native tests passed, 7 skipped (they need an isolated HTTP service and the like, not started this time), 0 failed", not "all tests passed".

List unverified parts separately under "Unproven boundaries" (see [release-record.md](../templates/release-record.md)).

## III. Process

### 1. Read-only research, no irreversible actions

Hotel price checks stop at the guest-details page, restaurant availability checks stop at choosing a time slot; no submitting forms, no sending email, no claiming coupons, no accepting agreements. When a third party needs to be contacted, draft the text and hand it to the user. This rule lets the agent run lots of queries safely.

### 2. Keep releases narrow

- Each release includes only the files changed this time, restricted by an allowlist; before releasing, verify that the old files in production match the expected baseline byte for byte, so you don't overwrite someone else's parallel update.
- Back up first (use SQLite's backup API for a consistent database snapshot), then install, and finally compare data fingerprints and the health check.
- Rollback restores only this release's code — **never overwrite updated data with an old full-database backup**.

### 3. Enable new shared data types in two phases

When adding a new kind of shared data (e.g. English address records in routes):

1. First deploy a server that can read and write the new type, with the server-side switch kept off; distribute an app that can read the new type.
2. Only **after confirming both phones have the compatible version installed**, turn on the server-side switch.
3. Turning the switch off only blocks new additions and edits; existing records are kept.

TestFlight showing "Ready to Test" or "Notified" is not proof of installation.

### 4. Keep a release record for every build

Record the scope of changes, exact test counts, whether the backend was released, archive and upload receipts, TestFlight status, and unproven boundaries. See the template at [release-record.md](../templates/release-record.md). Don't put keys, certificates, personal paths or private information in the record.

### 5. Write down conflicts and gaps

Source conflicts in research, prices you couldn't find, places without a suitable photo — write them all into the research record. The next round of research handles these first instead of starting over from scratch.

## IV. Product

### 1. Keep content offline inside the app

Networks are unreliable on a trip (around immigration, in the subway, in the mountains). Places, guides, the preparation checklist, phrases and reference post summaries are all bundled into the app and readable offline; the shared service only syncs the user's own edits.

### 2. The Today tab shows preparation items by date

- Preparation shows on the Today (`今日`) tab only when there are items "due today or earlier and still not done"; items with an empty `dueDate` show immediately.
- Items due in the future (e.g. the check the night before the return trip) don't interrupt early.
- Progress is still calculated over all items.
- The Today tab shows the full day's itinerary (in original order, including finished items and items with no time yet); don't cut it off at the current time — cutting it off makes users think the day is over when the return flight hasn't even taken off.

### 3. Show uncertainty

- Reservations required, partial closures, unconfirmed prices and conditional deals are marked with color + icon + text together.
- Booking status is always written as "at the time of the query it showed…", with the query time.
- A recommendation doesn't mean there's a table; adding it to the itinerary doesn't mean it's booked.

### 4. Don't automatically rewrite the user's saved itinerary

- Content updates, date rollovers and default changes must never automatically replace the user's edits.
- When deleting a booked meal or moving it to another day, clearly warn about the impact; also make it clear that actions in the app don't cancel or modify real bookings.
- Deleting an itinerary card doesn't delete tickets already saved.

### 5. Small interactions must actually be visible

The interaction feature's original feedback was just a tiny dot animation, and neither person noticed it in real use. Feedback must be obvious enough, with a fallback card when system notifications are suppressed.

### 6. Accessibility and large text

The largest accessibility text size exposes overlapping text, truncated date controls and buttons crammed into one row. Look at every new screen at the largest text size and in dark mode; map marker tap targets must be at least 44 pt. VoiceOver's actual reading order has to be verified on a real device; don't just check that labels exist.
